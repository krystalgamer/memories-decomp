## `func_80045514` at 0x80045514

`gcc_2_8_1_g8_split`, **437 of 437 instructions**, opcode multiset distance 4,
342 differing positions.
First reconstruction; there was no previous candidate and no rows in
`external_attempts.csv`. Not a near miss, but the instruction count is exact and
every remaining difference is localised to two clusters.

The descent was 386 instructions (51 short), 435 (2 short), 438 (1 long), then
437 with the counts equal.

The sound driver's command-state pump. It switches on the byte at
`g_SDValue->+0x7C` and, in most arms, clears that byte and the one at `+0x7D`
on the way out. `D_8009B460` points at a command block the arms fill in and
hand to `func_80014C40`.

## The dispatch is eight cases, not eighty-two

`jtbl_80010578` has `0x52` entries and the guard is `sltiu $v0,$v1,0x52`, but
the table holds only **eight distinct targets** besides the default. Indices
are the raw state byte:

| case | body | notes |
| --- | --- | --- |
| 17 | `0x80045764` | reached only from the `0x20` arm's `b7D == 1` path |
| 32 | `0x80045578` | the large arm; sub-dispatches on `+0x7D` |
| 33 | `0x80045804` | |
| 36 | `0x800458B0` | |
| 41, 42 | `0x800459EC` | two indices, one body |
| 72 | `0x80045A20` | the largest arm |
| 81 | `0x80045554` | two loads and a call |
| default | `0x80045BB8` | every other index |

**The bodies are laid out 81, 32, 17, 33, 36, 41/42, 72**, and GCC emits switch
arms in source order, so that is the order the cases have to be written in.
Numeric order is not the source order here, which is worth knowing before the
first draft: writing them ascending will misplace every arm.

Case 17's body sits between the 32 and 33 bodies rather than before them, which
is consistent with it being written as a `case 17:` label physically inside the
sequence rather than as a separate early case.

## The exit is three entry points into one tail

```
.L80045BA8   sb $zero,0x7D   ; j .L80045BD8      -> clears 7D only
.L80045BB8   sb $zero,0x7D   ; falls through     -> clears 7D then 7C
.L80045BC8   sb $zero,0x7C   ; falls through
.L80045BD8   lw $ra ; jr $ra ; addiu $sp,0x18
```

So there are three distinct exits - clear neither, clear `7D` only, clear both -
and they are stacked so that the "both" case falls into the "7C only" case.
Several arms reach `.L80045BC8` by `j` with the `sb $zero,0x7D` in the delay
slot, using a pointer they already hold; that is the same clear-both effect
written against a different register, so the source almost certainly has one
shared label per effect and GCC placed the blocks this way.

Reconstructing those three exits as three `goto` targets is the first thing to
get right, because every arm ends in one of them and their placement fixes the
whole tail of the function.

## Shapes to expect

- The `0x24` arm packs a 24-bit field and three bit-slices out of two words:
  `and` with `0xFFFFFF`, `and` with `0x1F000000` then `srl 24`, `srl 31`, and
  `srl 29`. Those are four separate stores to `0x531`, `0x530`, `0x532`, `0x533`.
- `0x1FFFFFF`-style masks are built with `lui`/`ori` and reused, so they are
  worth writing as one variable rather than repeated literals; this session's
  `Duel_LoadPackageStage` work showed variable reuse is what steers an
  expensive constant's register.
- Two arms call `func_80014C40(0, 0)` and branch on a non-zero result before
  doing anything else, which reads as a busy or lock test.

## The two levers that did the work

**Both pointer globals must be pushed out of small data.** The first draft
addressed `g_SDValue` and `D_8009B460` gp-relative under `-G8`, one instruction
per access. The target uses `%hi`/`%lo` everywhere: it has **52 `lui` against
the draft's 4**. Declaring both `extern` with
`__attribute__((section(".data")))` closes 48 of the 51 missing instructions in
one step.

That single opcode count was the whole diagnosis. A positional diff reported
420 differing lines and said nothing; the `lui` column said the addressing mode
was wrong, which is a property of the declaration rather than of any statement.

**The `+0x7D` sub-dispatches are `switch`, not `if`/`else` chains.** With
chains the build had two `bnez` and two `bne` where the target has `beqz` and
`beq` - the polarity signature this repository has already recorded for
`func_8004CB0C`. Writing both sub-dispatches as `switch (g_SDValue->b7D)` with
`case 0`, `case 1` and `default` fixed the polarity and took the differing count
from 407 to 320.

## Three more levers reached the exact count

**The jump table has to be zero-based, and an explicit `case 0` is what does
it.** With the lowest case at 17 GCC emits `addiu v1,v0,-17` before indexing and
builds a 65-entry table; the target indexes the raw byte against an 82-entry
table and has no subtract. Adding an empty `case 0:` that breaks out of the
switch moves `minval` to 0, removes the subtract, and makes the table the
target's size.

**`-msplit-addresses` is required, and the differing count hides it.** The
dispatch is `lui`, `addiu`, `sll`, `addu`, `lw` in the target and the assembler's
`$at` macro form in four instructions without the flag. `gcc_2_8_1_g8` scored
*better* on differing positions while being wrong here, which is a good reminder
that a positional count can prefer the wrong shape; the aligned streams named it
immediately.

**Whether a pointer global is cached in a local differs per block, and both
kinds appear in this function.** Case 32's fill keeps `g_SDValue` in one register
across five field loads, which only happens if it is read into a local - as a
global, each store through `D_8009B460` invalidates it and forces a reload. That
one change took the build from one long to exactly 437.

`D_8009B460` in the same block is the opposite: the target loads it **twice**,
once for the run of stores and once more for the `+0x1E` store. Caching it in a
local for the whole block gives one load and two instructions short; caching it
for the run and writing the last store through the global reproduces both loads.

So "cache the pointer" is not a property of the function. It is decided per
block, and the count of `lui`/`lw` pairs for that symbol is what decides it.

**One transcription error worth recording.** `+0x534` is set to `0xFFFF`, not to
zero; the constant is materialised in a branch delay slot two instructions
earlier, which is easy to attribute to the branch instead of the store.

## The exit blocks have to be written in the target's order

The function has three exits - clear neither, clear `+0x7D` only, clear both -
and the target stacks them so the "both" block falls into the "`+0x7C` only"
block while the "`+0x7D` only" block sits **above** them and jumps forward to
the epilogue.

Writing the "`+0x7D` only" label last, after the `return`, costs an extra `j`
and a pointer reload, because the block then has to jump backwards. Writing it
first, with an explicit `goto` from the end of the switch to the clear-both
label, reproduces the target's layout: 349 differing to 342, and it removed the
`j`/`nop` imbalance from the multiset.

Label order in the source is block order in the output whenever `goto` decides
the edges, so a shared tail should be transcribed in the order the target's
blocks appear rather than in whatever order reads most naturally.

## What is left

Multiset distance 4: one `jal` and one `sw` missing, one `lui` and one `lw`
surplus. That is a single call site, and it has been identified.

**The target makes six calls to `func_80014C40`; the build makes five.** The
build cross-jumps case 33's and case 36's command calls into one, because both
arms end in `cmd = 6`, an `arg` store, and the call. The target keeps them
apart:

```
case 33   lw v1,80(v0) ; li v0,6 ; sw v0,0(a0) ; addu a2,a2,v1 ; jal ; sw a2,4(a0)
case 36   lw v1,1320(v0) ; li v0,6 ; sw v0,0(a0) ;               jal ; sw v1,4(a0)
```

The delay slots store **different registers**, `$a2` against `$v1`, so the two
tails are not identical and cannot merge. This is the same mechanism recorded
for `Duel_LoadPackageStage`: cross-jumping runs after register allocation and
compares hard registers, so a register choice decides how many blocks exist.
Here it is worth exactly the missing `jal`/`sw` pair, and the surplus
`lui`/`lw` is the extra pointer reload the merged form needs.

The difference in the target comes from case 33 computing its argument with an
addition that lands in `$a2` while case 36 loads its argument straight into
`$v1`. Reproducing that split is the remaining work.

**Two smaller clusters, both scheduling.** Case 32's fill differs by one delay
slot, where the target leaves a `nop` after the `+0x74` load and the build fills
it with the `+0x1F` store. The tail of case 17 reloads `g_SDValue` after storing
`+0x7D`; writing the statements in the order the target *emits* them is worse
(388 differing, one instruction short), so that cluster is not transcription.

### Closed this round

- Hoisting case 33's `e->a` load into a local so it is live across the block,
  which is where the target loads it: **+4 instructions**, 352 differing. It
  costs a register.
- The same hoist with the mask applied mid-block, matching where the target
  puts its `and`, so the value accumulates load-mask-add exactly as the target
  does: **+5 instructions**, 372 differing. Worse than the plain hoist.

  Those two together say something useful. The target keeps that value live in
  `$a2` across the whole block at no cost, and this reconstruction cannot
  without spilling, so the block has **more competing live values than the
  target's does**. The register that decides the cross-jump is therefore
  downstream of a pressure difference rather than an allocation accident, and
  the next attempt should look for a value this source keeps alive that the
  target does not, instead of trying to place the accumulator directly.
- Reading case 17's flag word into a temporary before the `+0x7D` store: 388
  differing and one short.
