Advances one animation channel across every record of a track and returns the
record count. The `u16` at the second argument is a layout selector, and it is
switched on twice over the same eight values: once before the loop to pick the
two field offsets, the record stride and the per-record time step, and once per
record to pick between one and four halfwords whose largest is kept in the
maximum slot the fourth argument points at.

**Levers, in the order they paid.**

- *Both switches have to be written in the target's block-layout order, and
  they are not the same order.* The first switch's bodies run 9, 0x209,
  0xD+0x11, 0x20D+0x211, 0x15, 0x215; the second's run 9, 0x209, 0xD, 0x20D,
  0x11, 0x211, 0x15, 0x215. In the first, 0xD shares a body with 0x11 and
  0x20D with 0x211; in the second all eight are distinct. Writing either in
  numeric order moves every block.

- *The selector has to reach the switch through a `u32` local.* The target's
  dispatch tree uses `sltiu`, and a `u16` lvalue promoted to `int` gives
  `slti`. A cast in the switch expression is not enough -- `switch ((u32)*kind)`
  still emits signed compares. Assigning `k = *kind;` with `u32 k` first is
  what changes them, in both switches.

- *The stepped field is unsigned.* The target shifts it with `srl`, twice; an
  `s32` gives `sra` and the four-bit quotient that follows comes out signed.

- *There is no second walking pointer.* The maximum-slot reads are all
  negative displacements off a register that starts at `rec + 0x1C`, which is
  the giv `combine_givs` builds from the record pointer. Declaring an explicit
  `rp = rec + 0x1C` that walks alongside `rec` makes `rp` a second biv, so the
  offset-0 read uses it directly, is not recorded as a giv, and the giv base
  drops to `rp - 4`: every displacement then comes out four too high. Spelling
  the reads as `rec + 0xA` through `rec + 0x1C` leaves the base where the
  target has it. Worth five instructions and the whole displacement column.

- *The maximum chain alternates between storing after the test and storing
  inside it.* The target's three- and four-way cases run store-outside,
  store-inside, store-outside, then the shared tail:

  ```
      if (x < y) x = y;  *best = x;          /* store outside */
      if (x < y) { *best = y; x = y; }       /* store inside  */
      if (x < y) x = y;  *best = x;          /* store outside */
      y = ...; break;                        /* shared tail   */
  ```

  Writing all of them the same way lets cross-jumping merge blocks the target
  keeps apart and loses twelve instructions. Writing the inside form as
  `*best = y;` before `x = y;` rather than `x = y; *best = x;` is what keeps
  the merged suffix short enough in case 0x20D: with the store written as
  `*best = x` GCC hands both that block and case 0x15's a `sw` of the same
  pseudo and merges four instructions instead of three.

- *The loop tail order is `rec += stride; *total += step;` with the counter in
  the `while`.* Decrementing the counter as its own statement before the total
  update puts it ahead of the load in the tail and costs a `nop` in the load
  delay; `while (--n != -1)` lets the decrement fill that slot, as the target
  does.

**What is left** is three opcodes -- one `addu`, one `lhu`, one `slt` -- and
they are one cross-jump. Case 0x20D's last read and case 0x15's last read are
both `rec + 0x18`, so the two cases end in an identical `lhu`/`j`/`slt`
sequence. The target keeps both copies; this build merges them and case 0x20D
jumps into case 0x15's tail. The two blocks differ only in what precedes them,
and nothing in the source reaches that: writing case 0x20D's second store as
`*best = y` (which does break the four-instruction version of the same merge),
writing case 0x15's third store inside its test instead, a copy of the mode
argument, and `(s32)` on the loop's mode test all leave it where it is.
