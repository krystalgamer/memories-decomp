## `func_8004E7B0` at 0x8004E7B0

`gcc_2_8_1_g8`, 118 instructions against a target of 124, opcode distance 6.
The six are one repeated pair: the target keeps three separate copies of the
`0x60606061` division magic and this build keeps one. Everything else lines up.

A leaf. It reconciles the model view angles against the previous frame's
snapshot and writes two derived values, then saves the current angles as the
new snapshot.

`D_8009B478` is the live 8-byte view record (`+2` yaw at `D_8009B47A`, `+4`
pitch at `D_8009B47C`) and `D_8009B480` is the previous frame's copy of it
(`D_8009B482`, `D_8009B484`). The argument forces both updates even when the
corresponding delta is zero.

- Yaw: `dy = D_8009B47A - D_8009B482`, wrapped by a full turn when
  `|dy| > 0x800`. If forced or non-zero,
  `D_8009AF8E = (dy * 1280 / 384 + D_8009AF8E + m) % m`, where
  `m = *(u16 *)(D_8009AF88 + 0xA6)`. GCC turns the `/ 384` into the
  `0x2AAAAAAB` magic and the `* 1280` into `((x << 2) + x) << 8`; the `% m` is
  a real `div`/`mfhi` with both of GCC's zero and `INT_MIN / -1` traps.
- Pitch: if forced or `dz` is non-zero, a piecewise map of `D_8009B47C` into
  `D_8009AF90`, clamped to `+-0x139`: `(a * 26) / 85` below a quarter turn,
  `0x139` up to just past a half turn, then the negated forms
  `(-(x * 26)) / 85` within a quarter turn of the full turn and `-0x139`
  outside it. `/ 85` is the `0x60606061` magic with a shift of 5, and `* 26`
  is `((((x << 1) + x) << 2) + x) << 1`.
- Tail: an eight-byte `lwl`/`lwr` + `swl`/`swr` copy of `D_8009B478` over
  `D_8009B480`. That is a block move at alignment 1, so the copy has to go
  through a one-byte-aligned type - `struct { u8 b[8]; }` here. The existing
  siblings already declare these symbols as `u8` scalars and cast
  (`src/game/func_80058434.c`, `func_800592AC.c`), which is what makes the
  alignment 1.

The whole reconstruction is a fight against cross-jumping, and the useful part
of this entry is which spellings win it.

**The pitch map's five paths each need their own tail, or GCC merges them and
the function comes out seventeen instructions short.** The natural
`if`/`else if` chain writing one result variable and falling into a shared
store scores 107 of 124. Recovering the duplication takes two separate changes:

- *Each of the three arms that divides must write the divide out itself*
  (`D_8009AF90 = (-(u * 26)) / 85;` in the arm, not `v = ...; goto divide;`).
  Sharing the divide behind a label lets GCC hoist the arm-specific `* 26`
  into a single copy. Worth ten instructions. GCC still cross-jumps the
  `mult`/`sra`/`mfhi`/`sra`/`subu` suffix back together afterwards, which is
  what retail has.
- *Each clamp arm must set its result **before** the test that branches over
  it*, not inside the arm. Retail's two `-0x139` materialisations sit in
  branch delay slots, one on a `j` and one on a conditional `beqz`, so the two
  blocks are not the same shape and cross-jumping cannot merge them. Written
  as `if (cond) { r = -0x139; goto store; }` both arms become blocks ending in
  an unconditional jump, and GCC merges them into one. This is the
  "Initialise before the branch rather than in an else clause" rule doing
  duplication work rather than saving an instruction.

Together those take 107 to 118 and leave the alignment clean everywhere except
the magic constant.

## What is left

Six positions, all one cause. In each of the three dividing arms retail loads
the `0x60606061` magic *before* the arm's `* 26` shift chain:

```
lui $v1, 0x6060 / ori $v1, $v1, 0x6061 / <five-instruction *26> / mult
```

so the common suffix the cross-jumper merges begins at `mult` and each arm
keeps its own constant. This build emits the constant *after* the shift chain,
next to the `mult`, so `lui`/`ori`/`mult`/... is common to all three arms and
one copy survives in the merged block. The shift chains themselves are already
duplicated correctly, and the merged divide tail is correct; it is purely where
the constant load sits inside each arm.

Retail's third arm also carries its own `mult` in a `j` delay slot, retargeted
past the shared one - reorg duplicating an instruction into a slot, downstream
of the same three-copy layout.

Crossed without moving it: the natural `if`/`else if` chain and an exact-CFG
`goto` transcription (107 and 111); each dividing arm storing directly to
`D_8009AF90` instead of through the result variable (117); the same with the
clamp arms storing directly (120) and with all five storing directly (123, but
with the `0x139` arm then wrongly duplicating the store retail shares); reading
`D_8009B47C` inside each arm instead of through a local; the negation as a
separate statement from the multiply; and every GCC 2.8.1 profile. Of those,
`gcc_2_8_1_o1_g8` scores a nearer size (122) but a worse alignment - it
scatters the first block's scheduling - and `gcc_2_8_1_g0_no_sched1` scoring
488 of 496 bytes is a red herring, because `-G0` replaces each `%gp_rel` load
with a `lui`/`%lo` pair and coincidentally pads the count.
