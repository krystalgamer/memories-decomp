## `func_80046294` at 0x80046294

`gcc_2_8_1_g8_split`, 151 of 151 instructions, opcode distance 0, **18**
differing positions (the headline previously said 17; re-measured).

**Operand order is not the lever for the `0x20` arm.** The `addu $a0,$a2,$a1`
against retail's `addu $a0,$a1,$a2` looks like the operand-order class that
`(s32)` casts and shift-spelt subscripts reach elsewhere, and it is not: writing
the destination as `(SoundEntry *)(j + (u8 *)p)`, the source base as
`k + (u8 *)p`, and both together are each **byte-identical** to the baseline.
Computing the source before the destination in both arms costs 19. The ten
positions in the copy loop are a clean `$v0`/`$v1` inversion of the struct
copy's base pointer, which is where the next attempt belongs.

**One of the two pins is inert and has been removed from the source above.**
Subset-testing them rather than assuming both earn their place:

| pins kept | differing |
| --- | --- |
| `src_base` in `v1` + `src` in `a0` | 18 |
| `src_base` in `v1` only | **18, byte-identical** |
| `src` in `a0` only | 39 |
| neither | 39 |

So `src_base` carries the whole effect and the `src` pin does nothing at all -
dropping it leaves the function byte-for-byte identical with the multiset still
exact. Pinning `src` to `a1` instead is also byte-identical, which confirms the
variable is simply not the constraint. A pin that changes nothing is worse than
no pin: it looks like evidence, and the next reader has to re-derive that it is
not.

**The copy-loop inversion is not reachable by re-pinning `src_base` either.**
The ten positions are one clean `$v0`/`$v1` swap - retail puts the copy's base
in `$v0` and derives the loop pointer and end from it, the build puts the base
in `$v1` and derives them the other way round. The obvious move is therefore to
pin `src_base` to `v0`, since that is the register retail uses. Sweeping all
thirteen plausible registers, **`v1` is uniquely best at 18**; `a2`, `a3` and
`t0` give 31, `a1` 51, `a0` 54, and `v0` itself is worse than 55. The
function-wide reservation a pinned local takes is what defeats it: `v0` is
needed elsewhere in the function, so reserving it for the base costs far more
than the inversion is worth.

That leaves the inversion as a genuine allocation disagreement with no pin that
expresses it, which is the same wall `func_80023144` hit from the other side.

**The inversion survives every arrangement of the two pins that remain.**
`dst` is pinned to `v0` and `src_base` to `v1`, which is why the natural move -
putting the copy's base in `v0` where retail has it - cannot simply be pinned:
`v0` is already spoken for. Every way of rearranging that pair is worse:

| arrangement | differing |
| --- | --- |
| `dst` in `v0`, `src_base` in `v1` (stored) | **18** |
| the two swapped, `dst` in `v1` and `src_base` in `v0` | 37 |
| `dst` unpinned | 30 |
| `dst` in `a0` | 30 |
| `dst` in `v1`, `src_base` unchanged | 122, three short |
| `dst` unpinned and `src_base` in `v0` | 42 |

**The reference-count lever does not reach it either.** Folding `src_base` away
so `src` is computed in one expression, adding a reference by splitting the
constant add into its own statement, and moving the constant into the first
assignment measure 35, 26 and 35. That is the same result as on
`func_80012E5C` and for the same reason recorded there: the lever re-ranks
allocnos through `floor_log2(n_refs) * n_refs / live_length`, which moves
short-lived high-priority pseudos past one another, and `src_base` is a
long-lived pointer nowhere near the cliff.

So the ten copy-loop positions are an allocation disagreement that neither a
pin nor a re-ranking expresses: the register retail wants is held by another
pinned local whose own pin is load-bearing, and freeing it costs more than the
inversion. Together with the operand-order negative above, the function is
bounded at 18.

### That bound was wrong, and the reason is instructive: 18 to 8

The paragraph above is correct in every measurement and wrong in its
conclusion. It reads the sweep as "there is no pin that expresses the
inversion", when what the sweep actually shows is that there is no *single*
pin that expresses it - because the sweep only ever moved one variable at a
time.

Retail does not use one register for the copy's base. It uses **two**, one per
switch arm:

| arm | retail's `dst` | retail's `src_base` |
| --- | --- | --- |
| `0x42`/`0x43`/`0x45`/`0x46`/`0x48` | `$v0` | `$v1` |
| `0x20` | `$a0` | `$v0` |

`$v0` is not "held by `dst`" in the arm that needs it. It is held by `dst` in the
*other* arm. A single function-scope `register asm` variable is one pseudo and
therefore one hard register for the whole function, so it cannot be `$v0` in one
arm and `$a0` in the other - which is exactly the constraint `func_80057AF4`
records, and the fix is the same one: give the source as many variables as
retail uses registers, declared in per-arm blocks.

Wrapping each arm's copy in its own block and declaring `dst`/`src_base` inside
it takes **18 to 7**, with the multiset still exact. (It measured 8 until a
harness bug described below was fixed; one of those eight was never a real
difference.) The registers are the
content of the lever, not the split:

| arm 1 `dst`/`src_base` | arm 2 `dst2`/`src_base2` | differing |
| --- | --- | --- |
| `v0`/`v1` | `a0`/`v0` | **8** |
| `v0`/`v1` | `a0`/`v1` | 18 |
| `v0`/`v1` | `v0`/`v1` | 18 |
| `v0`/`v1` | `a0`/`a1` | 21 |

The two rows at 18 are worth noting: splitting the variables while keeping the
old registers reproduces the old result exactly, so the split on its own buys
nothing and the whole effect is `src_base2` reaching `$v0`.

**The general lesson is about the sweep, not the function.** A one-variable-at-
a-time register sweep cannot find a two-variable arrangement, and it reports a
clean "uniquely best" result that reads like exhaustion. Before concluding that
no pin expresses a disagreement, check how many distinct registers retail uses
for the value across the whole function; if it is more than one, no single pin
can express it and the sweep was answering a different question.

### What is left: seven positions, three causes

```
+0x020..+0x02C  the jump-table address is hoisted after the k/j initialisers,
                where retail emits it before them - four positions, one swap
+0x0CC          addu a0,a2,a1 for retail's addu a0,a1,a2 - commutative, and
                GCC canonicalises the operand order
+0x0DC/+0x0E0   in the 0x20 arm only, the dst increment and the src_base
                computation are still the wrong way round
```

An eighth position at `+0x0B8` was reported until the harness was corrected. It
was a local `j` whose `R_MIPS_26` relocation the harness misread; both build and
target jump to base + `0x118`. See the measurement note below.

### A harness bug that both invented and concealed differences

`objdump -r` prints a separate relocation block per section, and the harness
accepted any record without tracking which block it was in. This function's
jump table lives in `.rodata` and its entries are `R_MIPS_32` against `.text`,
so a `.rodata` entry whose offset collides with a `.text` offset silently
overrode the real relocation there.

The failure is not one-directional, which is what makes it worth recording:

| entry | before | after |
| --- | --- | --- |
| `func_80046294` | 8 | **7** - a false difference removed |
| `func_80015EF4` | 339 | **340** - a false match exposed |
| `func_80044838` | 285 | **288** - three false matches exposed |
| `func_80029934` | 230 | **231** - the note already said 231; the tool was wrong |

The three close candidates were re-checked against both versions and are
unaffected: `func_800283F4` holds at 2, `func_80023144` at 5, `func_80031874`
at 10. The fix is to track the `RELOCATION RECORDS FOR [section]` header and
only accept records under `.text`.


The last pair is the same shape the split fixed in the other arm, so it is the
most likely next position. Statement order does not reach it: computing the
source first, computing it last, and two intermediate arrangements all leave the
differing set at exactly `{0x020, 0x024, 0x028, 0x02C, 0x0B8, 0x0CC, 0x0DC,
0x0E0}` - identical position sets, not merely equal counts.


The instruction multiset is exact. Three differences remain and all three are
placement or register choice rather than shape:

- the `k` and `j` initialisers are emitted two instructions earlier than in the
  target, which puts them before the jump table hoist rather than after;
- `addu v1,v1,t0` sits one position earlier;
- the `0x20` arm computes its address as `addu a0,a2,a1` where the target has
  `addu a0,a1,a2`. `addu` is commutative and GCC canonicalises the operand
  order, so this one is probably not reachable from C at all.

it used the sibling's, so it is unpinned here. Four declaration orders, three
initialiser orders, four address spellings for the `0x20` arm, and seven
profiles were crossed at 17 without moving it.
