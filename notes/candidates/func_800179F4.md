## `func_800179F4` at 0x800179F4

`gcc_2_8_1_g8_split`, 240 of 240 instructions, opcode distance 4, 17
differing positions - one of which is the `gDuel_bTerrain`/`D_8009B364`
alias, which names the same address and links to the same word. The
whole sequence is retail's; what is left is which of two independent
`%hi` materialisations the first scheduling pass emits first, in three
places, plus the shape of one byte load.

the opponent id.

**What the shape needed.**

- *The sign bit has to be computed into a local before the object
  calls.* `side = (u32)gDuel_bOpponentID >> 31;` written between the
  first banner's flag store and `D_8009B214 = object;` is what makes it
  live across `func_8004002C`/`func_800400AC` and forces retail's third
  callee-saved register. Written inside the `func_800404CC` argument
  list it is evaluated after those calls, the function needs only two
  callee-saved registers, and the `sw $s2`/`lw $s2` pair disappears -
  two instructions short, and every position after the prologue shifts.
- *`gDuel_bTerrain[0]` is read twice.* Retail materialises `%hi` again
  for the `func_800404CC` argument; a single local read once is one
  instruction short there.
- *`gDuel_bOpponentID` is a scalar in `.data`, not an array.* All four
  reads then materialise the symbol freshly. Declared
  `extern s8 gDuel_bOpponentID[];` the base is hoisted into a
  callee-saved register for the whole function and the three plain
  reads lose their `lui`, which is three instructions short and moves
  the whole allocation.
- *The deck selection is a `goto` layout with a shared `deck_end = deck;`
  tail*, which is how the `>= 0` path and the `>= 0x27` path both reach
  `Duel_ShuffleBothDecks` through the same two-instruction block.

**Where the residual is.**

*The byte below `gDuel_bOpponentID` (4 positions).* Retail materialises
the symbol address into a register and loads at `-1` off it -
`lui` / `addiu %lo` / `lb -0x1($v0)`, three instructions. Every
non-volatile spelling measured folds the `-1` into the `%lo` and gives
two: `*((s8 *)&gDuel_bOpponentID - 1)`, a pointer local assigned to
`&gDuel_bOpponentID` and indexed `[-1]`, the same pointer decremented
first, `(s8 *)((u32)&gDuel_bOpponentID - 1)`, an index held in a local,
and the same index held in a `volatile` local. That is `LEGITIMIZE_ADDRESS`
under `-msplit-addresses` turning any `CONSTANT_P` address into a
`LO_SUM`, and cse propagating the pointer back into the memory operand
so it stays constant. A `volatile` cast on the load is the only thing
found that keeps the address in a register, but a volatile `QImode`
`MEM` also blocks combine from folding the sign extension into the
load, so it comes out `lbu` plus `sll 24` where retail has `lb`. The
stored source uses it because it is the closest measured state; the
right fix is whatever makes the address non-constant *without* the
volatile, and that is the open question on this function.

*Three `%hi` scheduling ties (10 positions).* In each, two independent
`lui`s are ready in the same cycle and retail emits the one whose chain
is shorter first:

- before the first `File_RequestAsyncTransfer`, `%hi(Duel_LoadPackageStage)`
  before `%hi(gDuel_bTerrain)` (2 positions);
- before the first `func_800404CC`, `%hi(gDuel_bTerrain)` before the
  `sw` of the fifth argument (3);
- around the life-point widget's two stores, `%hi(func_800164FC)` before
  the `lw` of `D_8009B21C` (5).

Inlining the terrain read into the call, moving the local, giving
`D_800E9DBC` its function-pointer-array type and swapping the two
widget stores all leave every one of them where it is, which is the
signature of sched1 rather than of source order - see "Two `%hi`
materialisations: sched1 picks the order, local-alloc picks the
registers" in `notes/research/matching-evidence.md`. The remaining two
positions are `%hi(D_801D1200)` landing in `$v0` instead of coalescing
with the `$a0` its `%lo` goes to, which follows from the third tie.
