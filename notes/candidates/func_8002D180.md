## `Main_RunAnimatedBattle` at 0x8002D180

`gcc_2_8_1_g8`, 85 instructions against a target of 86, opcode distance 1,
positional opcode diff 1. The single missing instruction is a load-delay `nop`.

The animated-battle frame driver. It sets the projection origin and screen
distance, then branches on two bits of the state byte `D_8009B26C`. On the
first entry, bit 0x40 clear, it latches that bit, raises `D_8009B0C0`, runs two
setup calls, and reads the first entry of the `D_800EF658` table. The sentinel
value 0x309 means there is nothing to animate, so it also latches bit 0x20 and
takes the short path. Otherwise it submits two model records and then a third
call carrying only `D_8009B364`. On later entries, bit 0x40 set, bit 0x20
selects which of two per-frame steppers runs, and a non-zero result tears the
sequence down and reloads the state byte from `D_8009B269`.

Three declaration facts drive the addressing, and they are the whole reason
this compiles to the right instruction forms.

**Three `u8` globals take three different addressing forms in one function.**
`D_8009B26C` and `D_8009B269` are plain scalar externs and reach `%gp_rel`
under `-G8`. `D_8009B0C0` carries `section(".data")`, which puts it outside
small data and produces the assembler `$at` macro form the target uses for its
store. `D_8009B364` is an incomplete-array extern, which is what splits its
address into a compiler register instead. Getting any one of these wrong
changes the instruction form at that site.

**`func_80053248` (now `Model_SetSlotProperties`) is variadic.** The matching
`src/game/model_set_slot_properties.c`
declares it `(s32 idx, ...)`, which is what allows the two six-argument calls
and the trailing two-argument call to coexist. That sibling also shows why
index 2 needs no further arguments: it takes the `else` arm that only consumes
the first.

**The table entry is an 8-byte record** of three `s16` followed by two `u8`.
The first record's fields are read before the sentinel test and the value is
reused as `f0 - 1` in the first call, so the load is shared rather than
repeated; advancing the cursor by one record between the two calls reproduces
the single `addiu $s0, $s0, 0x8`.

## What is left

One load-delay `nop` between `lbu %gp_rel(D_8009B269)` and
`sb %gp_rel(D_8009B26C)` in the teardown arm. This build emits the load and the
store adjacent with no pad; the target has the pad.

Tried without producing it: `volatile` on the source, on the destination, and
on both; routing the value through a temporary; and every GCC 2.8.1 profile.
Declaring `D_8009B269` as an incomplete array does reach the exact length of
86, but it moves that access off `%gp_rel` into a register form the target does
not use, trading one missing pad for two wrong instruction forms, so it is a
worse base despite the exact length.
