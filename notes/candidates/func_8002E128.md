## `func_8002E128` at 0x8002E128

`gcc_2_8_1_g0`, 146 of 146 instructions, opcode distance 0, 13 differing
positions, and identical at 13 under every g0 and g8 profile.

The script image-set loader, the function after `func_8002E060` in the same
translation unit as `script_image_objects.c`. A negative value re-reads the
owner's stored value at +0x3C and the value is stored back either way. At
0x200 and above it takes a fresh display object (`func_8004002C` then
`func_800400AC` with 3), lays it out with the ten-argument `func_80040510`,
sets bit 24 of its +4 word, clears bit 3 of its +8 halfword, marks the owner
active and hands it the object, then reads the six-byte `D_80090C00` entry
for `((value >> 4) & 15) * 10 + (value & 15)`: bit 0 creates the second
image (`func_8002E060` with 0x14, 1) and copies bytes 1 and 2 into its +0x30
and +0x32, bit 1 creates the third (0x16, 2), copies bytes 3 and 4 the same
way and byte 5 into the owner's +0x2C, and bit 7 then sets bit 3 in that
object's +8 halfword. Below 0x200 it creates the owner's own object (0x10,
0), zeroes the two image pointers below 0x100, and otherwise reads the
two-byte `D_80090BA8` entry for the same index: bit 0 creates the second
image (0x12, 1), bit 1 the third (0x14, 2) with byte 1 into +0x2C.

Six canonical attempts, all 8 instructions short at 552 of 584 bytes. This
is the first exact multiset. Nothing structural is left: every one of the
thirteen positions is `$v0`/`$v1` naming or scheduling inside the block
between the layout call and the first entry test, plus the order of the
`lui`/`addiu` against the `sll` in the below-0x200 branch.

**What the shape needed.**

- *The index is assigned back into `value` in the upper branch only.* That
  is what keeps it in `$s1` across the object updates. In the lower branch
  the index is a temporary and the entry's flag byte takes `$s1` instead, so
  the lower branch reads `flags = object[0]` into its own local.
- *The table pointer is assigned into `object`.* Retail keeps both in `$s0`
  back to back (`sw $s0, 0($s2)` then `addu $s0`); a second pointer local
  gets a fourth callee-saved register and shifts the frame.
- *The lower branch is `if (value >= 0x100) { table } else { zeroes }`,*
  which places the two zero stores out of line at the end as retail has
  them.
- *The object updates come before the owner stores.* The two objects have
  unknown bases, so the stores are ordered by may-alias output dependences
  and the source order fixes the emitted order across them.

**Crossed without moving the residual.** All six orders of the three owner
stores against the object updates and three placements of the table
computation; the index as a separate local in both branches; the flag byte
through `value`; a `u16` array reference for `D_80090BA8`; struct-typed
accesses for the object, the owner, and both; every g0 and g8 profile.

**Where the residual is.** Retail materialises the `1` for `owner[0x10]`
before the object's halfword store, walks the `* 6` chain in `$v1` with the
1 still live in `$v0`, stores the byte after the chain, and only then
materialises the table address in `$v0`. The build launches the `1` right
before its store (a single-set pseudo gets launch priority in the backward
scheduler once its use is placed), so the chain takes `$v0`, the address
`$v1`, and the byte store lands after the pointer store. The `-dS` trace
shows the tie: the byte store, the pointer store, the table `addu` and the
final halfword store all sit at priority 2 and the hazard rule then prefers
the store. Retail needs that byte store at priority 1, which no owner or
object spelling produced.

**Allocation crossed as well as scheduling.** The residual reads like the
`$v0`/`$v1` inversion that closed `func_80057AF4` and `func_800179F4`, and it is
not one. Naming the `* 6` product and the `D_80090C00` base as locals and
pinning them to retail's `$v1` and `$v0` measures 16 against 13; naming them
without pins is 13; either one alone is 14. Holding the `1` for `owner[0x10]`
in a `$v0`-pinned local is 19, unpinned 13. Hoisting the lower branch's table
base above the index computation is 19, and combined with the pinned `1`, 25.

So every pin here is worse than no pin, which is the signature of a scheduling
tie rather than an allocation one: the registers follow the order, not the other
way round. That is consistent with the `-dS` reading below, and it means the
entry should not be re-attacked from the allocation side.
