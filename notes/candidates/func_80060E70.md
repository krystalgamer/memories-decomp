the style register and branches on it, so an empty slot leaves the style at
zero with no extra instruction. Writing `style = 0;` and testing `e[0]`
separately costs a `move`. Loading `style = e[0]` and testing `style` removes

**The entry list is walked by two `u16 *` cursors and the first is the
parameter.** The target copies `$a0` into `$s3` at the second instruction of

the row base in the cursor and folds `0xA` into every displacement. A `u16 *`

instead, which is one instruction longer and moves three accesses. Walking a
`Slot *` forward two bytes per iteration and writing `w->fA[0]` gives the
target's form.

zeroed explicitly first: counter, flag cursor, pitch, row cursor. Permuting

target's forms, a fresh `lui`/`%lo` pair for `[0]` and the held base for `[1]`.
The difference is only that the target computes that base at the top of the

The residual has a shape worth naming: the setup block is emitted in **exact
reverse**, mirrored about `move $s0, $s4`.

    addiu $s8, $v0, %lo(...)   move  $s5, $s2
    move  $s0, $s4             move  $s0, $s4

    addiu $s1, $s3, 2          addiu $s8, $v0, %lo(...)

It *looks* like the store block in `func_80045334`, where the reversal was
traced to `sched2`. **It is not the same cause, and the resemblance is
misleading.** Building with `-fno-schedule-insns2` leaves this block
byte-identical -- same five instructions, same reversed order -- and moves only
prologue positions. `sched2` never touches it.

The cause is the loop pass. GCC hoists the one loop invariant with
`emit_insn_before (..., loop_start)`, which places it immediately before the
loop and therefore *after* the four setup assignments that already sit in the
preheader. The target has the same hoist at the head of that block. So this is
an insertion-point difference in loop invariant motion, not a scheduling
decision, and the two functions do not share a lever.

Read against the target the residual is narrower than "a placement choice".
The target hoists exactly one loop invariant, the `D_801D5608` base into `$fp`,
and materialises `gDuel_adwCardStats` *fresh inside the loop* each iteration in
`$t0` rather than hoisting it. This build already agrees on both of those, and
on the register each lands in. The single difference is that GCC's loop pass
emits the hoisted pair immediately before the loop, so it is **appended** to
the four setup assignments, where the target has it **prepended**.
