## The four facts that reached distance 0

**The style variable is the card id.** The target loads the id straight into
the style register and branches on it, so an empty slot leaves the style at
zero with no extra instruction. Writing `style = 0;` and testing `e[0]`
separately costs a `move`. Loading `style = e[0]` and testing `style` removes
it.

**The entry list is walked by two `u16 *` cursors and the first is the
parameter.** The target copies `$a0` into `$s3` at the second instruction of
the prologue, then derives `$s1 = $s3 + 2`. Advancing the parameter directly
and deriving only the flag cursor from it reproduces that.

**The row's id array is walked by a `Slot *`, not a `u16 *`.** The target keeps
the row base in the cursor and folds `0xA` into every displacement. A `u16 *`
set to `s->fA` puts `s + 0xA` in the register and uses displacement zero
instead, which is one instruction longer and moves three accesses. Walking a
`Slot *` forward two bytes per iteration and writing `w->fA[0]` gives the
target's form.

**The setup statements must run in the target's order,** with the loop counter
zeroed explicitly first: counter, flag cursor, pitch, row cursor. Permuting
those four is worth seven words on its own.

The profile is `_split` with `-fno-strength-reduce`. The plain profiles put
`gDuel_adwCardStats` through the assembler `$at` macro where the target uses a
compiler register, and strength reduction rewrites the loop bound away from the
`slti $v0, $s2, 0x7` the target keeps. Both halves of that had to be re-swept
after the cursor change; on the previous base the non-split profiles won.

**The two cursor advances must be written `q` before `e`.** The target ends the
loop body with `addiu $s1, $s1, 4` then `addiu $s3, $s3, 4`; writing
`e += 2; q += 2;` emits them the other way round. Swapping the two statements is
worth two words on its own and is what takes this entry from 6 to 4. Nothing
else changes.

## What is left

Four words, one placement choice. Both `D_801D5608` stores already take the
target's forms, a fresh `lui`/`%lo` pair for `[0]` and the held base for `[1]`.
The difference is only that the target computes that base at the top of the
setup block, before the row cursor and the pitch, while GCC hoists it to the
bottom here, so the four setup registers come out permuted and the two entry
cursors swap names.

The residual has a shape worth naming: the setup block is emitted in **exact
reverse**, mirrored about `move $s0, $s4`.

    target                     this build
    lui   $v0, %hi(...)        addiu $s1, $s3, 2
    addiu $s8, $v0, %lo(...)   move  $s5, $s2
    move  $s0, $s4             move  $s0, $s4
    move  $s5, $s2             lui   $v0, %hi(...)
    addiu $s1, $s3, 2          addiu $s8, $v0, %lo(...)

It *looks* like the store block in `func_80045334`, where the reversal was
traced to `sched2`. **It is not the same cause, and the resemblance is
misleading.** Building with `-fno-schedule-insns2` leaves this block
byte-identical -- same five instructions, same reversed order -- and moves only
prologue positions. `sched2` never touches it.

The cause is the loop pass. GCC hoists the one loop invariant with
`emit_insn_before (..., loop_start)`, which places it immediately before the
loop and therefore *after* the four setup assignments that already sit in the
preheader. The target has the same hoist at the head of that block. So this is
an insertion-point difference in loop invariant motion, not a scheduling
decision, and the two functions do not share a lever.

Read against the target the residual is narrower than "a placement choice".
The target hoists exactly one loop invariant, the `D_801D5608` base into `$fp`,
and materialises `gDuel_adwCardStats` *fresh inside the loop* each iteration in
`$t0` rather than hoisting it. This build already agrees on both of those, and
on the register each lands in. The single difference is that GCC's loop pass
emits the hoisted pair immediately before the loop, so it is **appended** to
the four setup assignments, where the target has it **prepended**.

## Where the preheader order comes from, and why four is the floor as written

Re-measured with relocations resolved: four differing positions, all in the
loop preheader, and the whole body is exact. The preheader holds the same five
instructions in both builds, in reversed group order:

```
built    addiu $s1,$s3,2   move $s5,$s2   move $s0,$s4   lui/addiu $s8
target   lui/addiu $s8     move $s0,$s4   move $s5,$s2   addiu $s1,$s3,2
```

Two separate things are going on and they were previously conflated.

**The order of the three initialisations is source order.** Writing them as
`w = s; y = 0; q = e + 1;` reproduces the target's `move $s0` / `move $s5` /
`addiu $s1` exactly. That alone takes the residual from four positions to a
three-instruction shift.

**The address hoist is placed by loop-invariant motion, which appends.** It
inserts before `loop_start`, so it lands after anything the source already put
in the preheader, and no source order can put it first. It is also invariant to
both schedulers: `-fno-schedule-insns`, `-fno-schedule-insns2`, and both
together leave the preheader untouched, so this is not a scheduling question.

**What separates the two groups is biv versus giv.** Compiling the same source
with strength reduction enabled moves exactly one initialisation - `w`, which
becomes the derived `$s4 + 10` - to *after* the hoist, and leaves `y` and `q`
before it. So plain induction variables keep their source position in the
preheader, and derived ones are initialised after the invariants. The target
has all three after the hoist, which says all three are derived in the original
translation unit.

Rewriting the loop index-based so all three become derived does reproduce the
`[hoist][inits]` order - confirmed in the preheader of that build - but costs
far more than it saves, because the same rewrite makes GCC fold the `+10` into
the base (`addiu $s0,$s4,10` with `sh $v0,0($s0)`, against the target's
`move $s0,$s4` with `sh $v0,10($s0)`) and re-derives the `e` accesses. Scored
62 to 63 across the split profiles, against 4 for the pointer-increment
spelling. Pinning the four derived variables to the target's registers made it
101.

Also crossed without improving on four: an explicit `s32 *t = D_801D5608` in
place of the array spelling, with and without a pin to `$30`, and with
`gDuel_adwCardStats` made `volatile` or pushed to `.data` to stop it being
hoisted instead. All land between 53 and 67. The array spelling is required for
a second reason worth recording: the target materialises `D_801D5608[0]`
inline as `lui` plus `sw ...,%lo(sym)(reg)` and reaches `[1]` through the
hoisted pointer at `+4`. A pointer variable makes both go through the pointer
and loses the inline form.
