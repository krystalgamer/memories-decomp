## `func_8005C1F4` at 0x8005C1F4

`gcc_2_8_1_g8`, 94 instructions against a target of 96, opcode distance 2.
Supersedes the 97/96 distance-3 entry below it, which is kept because its
reading of the surrounding code is still the right one.

The `DecDCTout` callback, registered by `src/game/func_8005B8A0.c`, which is
the sibling to copy conventions from: it declares `D_8009B498` as `u8 *` and
adds large literal offsets to it directly.

Each call copies the current strip header into the ring slot for
`D_8009B067`, hands that slot and the matching frame buffer to `LoadImage`,
advances the index modulo four, then accumulates the strip height. While the
accumulated height is still short of the frame height it queues the next
decode with `DecDCTout`; otherwise it raises `D_8009B062`.

**Three corrections to the previous entry.**

- *The header copy is one eight-byte aggregate, not two four-byte ones.*
  Written as two `Bytes4` assignments the copy comes out as load, store, load,
  store with a load-delay `nop` after each load; retail issues both `lwl`/`lwr`
  pairs and then both `swl`/`swr` pairs, which is what a single eight-byte
  aggregate copy gives. `RECT` is the natural type - it is what `LoadImage`
  takes, it is eight bytes, and its `short` members give it alignment 2, which
  is why GCC cannot use aligned words. That is worth two instructions and the
  whole shape of the block.
- *`D_800F5D44` has to be kept out of small data.* It is four bytes, so under
  `-G8` a plain `extern s32` declaration puts it in `sdata` and both accesses
  come out `%gp_rel`; retail reaches it through `lui %hi` / `%lo`.
  `__attribute__((section(".data")))` on the scalar is the form - see
  "Small-data addressing: one mechanism, five levers" in
  `notes/research/matching-evidence.md`. The three genuinely small globals in
  this function (`D_8009B060`, `D_8009B067`, `D_8009B498`) *are* `%gp_rel` and
  keep their plain declarations, so the function needs both answers at once.
- *The copy's destination is expressed off the `0x40000` base too.* The
  previous entry had the source at `h + 0x2428` with `h = base + 0x40000` but
  the destination at `base + 0x42400 + idx * 8`, which folds the offset into
  the store displacement. Retail computes `base + idx * 8 + 0x40000` and stores
  at displacement `0x2400`, so both ends of the copy hang off the same base.
  `LoadImage`'s first argument keeps the `0x42400` spelling: it is the same
  address computed a second way, and retail computes it a second time.

Together these take the entry from 97/96 at distance 3 to 94/96 at distance 2,
with the copy block, the modulo-four advance and the whole tail exact.

**What is left is two instructions, and they are one fact.** Retail does not
share the `idx * 8` between `LoadImage`'s first argument and the copy address.
It consumes the first one into `$a0` immediately, then, for the copy, makes a
register copy of the index and a register copy of the base and recomputes the
shift:

```
addu $v0, $v1, $zero      # idx
addu $v1, $a2, $zero      # base
sll  $v0, $v0, 3
addu $v0, $v1, $v0
addu $v0, $v0, $s0
addu $v1, $v1, $s0
```

Every spelling measured lets cse share the single `idx * 8` and reach the same
two addresses in three instructions instead of six, which is two short once
`LoadImage`'s second argument moves into the delay slot: a `d` local against
the address written inline, the same for the source operand, both inline
(98 - two *too many*), `(RECT *)(base + 0x42400) + idx` for the argument,
`((RECT *)(h + 0x2400))[idx]` for the destination, both together, `slot` and
`frame` locals computed before the copy, and pins on `idx` to `$3` and on
`base` to `$6`. The two register copies look like an allocation shuffle rather
than anything the source asks for, but the recomputed shift is not - it means
retail's two addresses were not common subexpressions when cse ran.

### Previous entry: 97 of 96, opcode distance 3

`gcc_2_8_1_g8`, 97 instructions against a target of 96, opcode distance 3.

The `DecDCTout` callback, registered by `src/game/func_8005B8A0.c`, which is
the sibling to copy conventions from: it declares `D_8009B498` as `u8 *` and
adds large literal offsets to it directly.

Each call copies the current strip header into the ring slot for
`D_8009B067`, hands that slot and the matching frame buffer to `LoadImage`,
advances the index modulo four, then accumulates the strip height. While the
accumulated height is still short of the frame height it queues the next
decode with `DecDCTout`; otherwise it raises `D_8009B062`.

Three shape facts, two of which are already recorded elsewhere.

**The header copy is byte-aligned.** Eight bytes move as two `lwl`/`lwr` and
`swl`/`swr` pairs, so the source is a struct of `u8`, not a word type. The
sibling already defines `typedef struct { u8 b[4]; } Bytes4;` for exactly this,
and two assignments of it reproduce the block. Same fact as `func_8003B5C8`
and `func_80058938`.

**The index advance is a signed `% 4`.** It compiles to the branch plus
`andi 0x1FC` form rather than a plain mask, because GCC narrows the constant to
the known range of the value rather than using `~3`.

**The window needs a high-half base at `0x40000`, not at `0x42400`.** The
target holds `lui $s0, 0x4` with no `ori` and reaches every halfword through
displacements `0x2420`..`0x242E`. Writing the pointer as `base + 0x40000` and
the fields as `h + 0x2428` and so on reproduces that; a pointer at
`base + 0x42400` with small displacements does not, and costs a position.

The profile is `gcc_2_8_1_g8`, not the `_split` variant the rest of this family
uses. On the split profiles this same source is distance 6, so the usual
inheritance would have picked the worse one here.

What remains is one `addu` missing against one `swr` and one `nop` extra, all
in the header copy: the target completes the destination address with a
separate `addu` where this build folds it into the store displacement.
