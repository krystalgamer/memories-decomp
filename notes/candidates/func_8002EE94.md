### The constant cluster is bounded: one separator, one reload

Two facts together bound this cluster, and neither is a list of failures.

**A reload happens only when a store intervenes between a field write and its
read.** GCC otherwise knows what it just stored and satisfies the argument from
the constant. That is why the current source reloads the *first* field: the
`D_8009B27C` store sits between its write and its read.

**The arm contains exactly one statement that can serve as that separator.**
Written out, the arm is two field writes, the flag store, and the call. The
call's own argument setup cannot separate anything because GCC emits it at the
call, and the flag store is a single halfword write that cannot be split.

So at most one of the two reloads is reachable, and only the first. The three
placements of the flag store exhaust the arrangement:

| flag store | result |
| --- | --- |
| before both field writes | 12, no reload |
| **between the two field writes** | **11, the first field reloads** |
| after both field writes | 355 of 359 - both arms' tails become the same `TextBox_SetPos` call and GCC cross-jumps them, losing both reloads |

Retail's arm has both reloads *and* the flag store after them, which is the one
arrangement this source cannot express: reaching it needs the reads to be
statements of their own before the flag store, and binding them to locals is

removes the reload the build already had.

That is a genuine bound rather than an exhausted search - the obstacle is that
the arm has one separator and needs two.

### Five of the seventeen were a harness bug: relocation addends

Four `D_8009B2A4[1]` references and one more were never differences. MIPS uses
REL relocations, so the addend lives in the instruction's own immediate field,
and the harness was replacing the whole immediate with the symbol's value -
discarding it. `D_8009B2A4` resolves to `gp + 924`; the element at index 1 is
`gp + 926`, and the build's instruction carried the `2` that got thrown away.

The fix is to add the instruction's sign-extended immediate to the symbol value
for `LO16` and `GPREL16`, take the `R_MIPS_26` addend from the encoded target,
and for `HI16` pick up the low half of the addend from its paired `LO16`.

**Controlled before being believed.** Sixty already-matched functions were
re-measured with the corrected resolver and all sixty still report zero. A
resolver change that made a difference disappear would do the same to a real
one, so the control is what makes the new figure trustworthy rather than merely
smaller.

### Store order here is worth 168 positions

The one missing `lh` is the read-back of the second coordinate. Retail writes
`0x38` to `+0x32` and loads it straight back into `$a2`; the build keeps the
constant in a register and copies it, which is the extra `move`. The stored
source already spells both read-backs as struct reads, so GCC is forwarding one
store to its load and not the other.

Two attempts to defeat that forwarding, both far worse:

| variant | result |
| --- | --- |
| baseline | 13 |
| the two coordinate reads bound to locals, interleaved with their stores | 181 |
| **the two adjacent coordinate stores swapped, nothing else changed** | **181** |

The second row is the one worth keeping. It differs from the baseline by
exactly one thing - the order of two adjacent stores through the same pointer -
and costs **168 positions**. That is the ordering rule corrected on
`func_80028B08` showing its full magnitude: source order *is* dependence order
for memory operations the compiler cannot prove disjoint, and there it was
worth 6 positions, which understates it badly. On this function the same rule
is worth more than ten times as much, in the punishing direction.

So the store order in the stored source is not incidental and must not be
tidied. Anyone reformatting this block will lose 168 positions and have no
indication why.

**A third ordering attempt, and a caution about reading emitted order as source
order.** Retail *emits* the two coordinate stores and their read-backs before
the `D_8009B27C` store, while the stored source writes the global first. That
looks like an obvious thing to correct, and it is wrong: moving the global's
store below the coordinate work scores **179 and is four instructions short**.

The reason is worth keeping, because the inference is tempting. GCC can tell a
`$gp`-relative global from a store through a pointer, so those two stores are
*not* mutually ordered and the scheduler is free to place the global's store
where it likes - which is why retail's emitted order differs from its source
order here. Emitted order is evidence of source order only for operations the
compiler is *obliged* to keep in order, and this pair is not one. Moving it
instead lengthens `flags`' live range across the block, which is where the four
instructions and the other 166 positions go.

That is the same distinction as the two-adjacent-stores result above, applied
in the opposite direction: both stores through `obj` are dependence-ordered and
their order is load-bearing, while the global's store beside them is free and
its emitted position says nothing about the source.

**`volatile` is not the way to force the read-back.** A stored value that
retail reads straight back is elsewhere in these notes a `volatile` signature,

it fails badly here. Four placements - volatile on the two reads with the flag

The reason is that `volatile` does not just preserve the one load; it
suppresses the surrounding optimisation that the rest of this arm depends on.
Where the signature applies, the value is read back and nothing else about the
block changes. Here the block's shape is itself the thing being matched, so a
barrier that big destroys more than it fixes.

That leaves the trilemma in the section above intact, and now with a fourth

**The three options are a cycle, not a menu.** Option 1 was re-measured at
355 instructions and 101 differing, confirming the four-short figure, and the
cross-jumping lever that works elsewhere in this repo - writing one arm so its
tail is not a duplicate - does **not** apply. Adding a `goto` out of the arm to
a shared `return` leaves it byte-for-byte at 355/101, because the tail really is
identical: two `lh`, the argument move and the `jal`.

Comparing against retail shows why retail does not merge it, and the answer
closes the loop. Retail's arm is

```
lh   $a1, 0x30($s1)     <- first argument loaded early
li   $v0, 0x38
sh   $v0, 0x32($s1)
lh   $a2, 0x32($s1)     <- second argument loaded early
andi $v0, $v1, 0xDFFF
sh   $v0, %gp_rel(D_8009B27C)($gp)   <- flag store between the loads and the call
jal  TextBox_SetPos
```

so the suffix before the `jal` is the flag store, not the two loads, and there
is nothing for cross-jumping to match against the shared block. **The
discriminator is that both arguments are loaded before the flag store rather
than at the call.** Getting them there means binding them to locals, which is
option 2, whose blocker is that gcc then constant-propagates the values it just
stored.

So the three options are not independent choices to be traded off. Option 1's
blocker is fixed by moving the loads early; moving the loads early *is* option
2; option 2's blocker is the propagation; and suppressing the propagation with
`volatile` is the fourth option closed above, which costs four instructions.
Each fix triggers the next one's blocker. Anything that reaches this arm has to
break the cycle by preserving a store-to-load forward without a barrier, and no
spelling tried so far does.

### Levers that got it here

- **`D_8009B2A4` must be a sized array**, `extern u16 D_8009B2A4[2];`. Unsized,
  the `+2` store leaves small data and comes out as a materialised `%hi`/`%lo`
  pair instead of retail's `%gp_rel(D_8009B2A4 + 0x2)`.
- **`DuelEffect_HasActiveEntry` takes the channel.** Its argument is what makes
  gcc materialise `&D_800EB0F8[0]` into `$a0` before reading `flags_34` through
  it; declared `(void)` the read collapses into a single `lui`-based load.
- **Compute a flag value before the store that follows it.** `D_8009B27C |=
  0x6000` written after the object store lands in `$v0` and cross-jumping
  merges its `sb` with the switch's shared store at the end of the function.
  Computed into a local first it stays in `$v1` across the store and keeps its
  own `sh`, which is retail.
- **Reload the object pointer into its own local after the call that uses it.**
  `func_80043178(box->field_28)` followed by a store through `box->field_28`
  gives one `lw`; retail has two, and binding the second read to a local
  restores it along with retail's `$a0`/`$v0`/`$v1` assignment in that block.
- **Short-lived channel pointers need their own locals**: `&D_800EB0F8[2]` for
  the prompt, otherwise gcc derives it from the `&D_800EB0F8[3]` base already
  in a register and the offsets come out as 200 and 252.
- **The box pointer has to be pinned to `$s0`.** Unpinned, gcc gives the box
  `$s1` and the object `$s0`, the opposite of retail, and every access in the
  second half shifts.
