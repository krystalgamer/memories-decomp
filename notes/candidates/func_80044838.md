## `func_80044838` at 0x80044838

The memory-card I/O driver's per-frame step, called with a "poll or wait" flag
and two out-pointers. It gates on `_card_status` or `_card_wait`, then
dispatches on `D_8009B43E - 1` through `jtbl_80010548`:

| state | table entry | what it does |
|---|---|---|
| 1, 2 | 0x800448E4 | pump `func_80044608` until it returns non-negative |
| 3, 4 | 0x800449B4 | sub-state machine: poll, then `open`/`lseek`/`read` or `write`/`close` on `D_800F2B00` with ten retries each |
| 5, 6, 7 | finish | nothing |
| 8 | 0x80044B70 | poll, bounds-check `D_8009B438 + D_8009B434` against 0x10, write the directory entry with `func_80044470`, then reopen the file to commit |
| 9, 10 | finish | nothing |
| 11, 12 | 0x800448FC | sub-state machine: poll, then `_card_read` or `_card_write` of block `D_8009B44C` |

States 3/4 and 11/12 share the sub-state dispatch tail (`if (sub == 2) goto
retry_wait;`) because both are three-case switches on `D_8009B44F` with the
same default, and gcc cross-jumps the two tails.

**What is left is 9 instructions, all of them the same cause.** Retail keeps
three separate `sw $v0, %gp_rel(gMemCard_nIOResult)($gp)` / `j` / `nop` tails,
for result codes 2, 6 and 7. This build cross-jumps all three onto one shared
store, which is 3 instructions each for the 6 and 7 paths and accounts for 6 of
the 9; the remaining 3 are the callee-saved register (`$s6`) and the argument
copies that the extra live values pay for. Retail *does* cross-jump the three
`code = 2` sites onto one tail, so the difference is not that its build had
cross-jumping off - it merged the identical blocks and left the ones that
differ only in the constant alone.

A probe confirms the diagnosis rather than fixing it: aliasing the 6 and 7
stores as non-volatile against the volatile `gMemCard_nIOResult` makes their
MEMs unequal, cross-jumping stops, and the build goes 286 -> 289. That is a
compiler trick and not a plausible source shape, so it is recorded here as
evidence and not used.

### The nine missing instructions are one variable, not nine placements

Re-measured from the stored source: 286 against 295, opcode multiset distance
21, dominated by `nop -6` and `sw -4`. The `lui` count is 6 against 7, which
**rules out an addressing-mode error** - the diagnostic that explained
`func_80045514`'s 51-instruction deficit does not apply here.

**The target saves one more callee-saved register than this build.** It saves
`$s0` through `$s6`; the build saves `$s0` through `$s5`. That extra register is
not a pointer: the target has no store through `$s4`, while this build has
`sw $v0,0($s4)`. So the target keeps an extra *value* live across calls and this
reconstruction does not.

**What the value is.** The target writes `gMemCard_nIOResult` five times, and
not one of those stores carries a literal:

```
sw $v0, %gp_rel(gMemCard_nIOResult)    x3
sw $zero, %gp_rel(gMemCard_nIOResult)  x1
sw $s4, %gp_rel(gMemCard_nIOResult)    x1
```

The stored source assigns literals instead - `= 2` in five places, plus `7`, `6`
and `0` - and GCC cross-jumps the identical ones, so eight assignments collapse
to five references in the output. The reference counts end up close; the shapes
do not match at all.

**Corrected: it is not a result local, and the direct test of that failed.**
Reading the target more closely, `$s4` is loaded in the retry loop's *preheader*

```
.L80044C38   lui $s3,%hi(D_800F2B00)   ; addiu $s2,$zero,-1 ; addiu $s4,$zero,2
.L80044C44   ... jal open ... bne $s1,$s2 ... bgez $s0,.L80044C44
             ... sw $s4, %gp_rel(gMemCard_nIOResult)
```

so the constant `2` is materialised **before** a loop containing a call and
therefore has to live in a callee-saved register. Three values are hoisted
there: the string's `%hi`, `-1` for the `fd != -1` test, and `2`.

Assigning a local `result = 2` before the loop and storing it after is
**inert** - still 286 and 283 differing. GCC propagates the constant back to
the store, which is the same cheap-immediate boundary recorded on
`Duel_LoadPackageStage`: variable reuse steers registers only for constants
expensive enough to survive as a value, and `2` is not one.

**And the store is not a literal at all in two of the arms.** `.L80044BAC` is a
jump target reached by `bnez $v0` from two places, and in both the `$v0` being
tested is the **return value of `func_80044608`**:

```
jal func_80044608 ; bltz $v0,... ; bnez $v0,.L80044BAC
.L80044BAC   sw $v0, %gp_rel(gMemCard_nIOResult)
```

The stored source writes `gMemCard_nIOResult = 2;` in both, where the target
writes the call's result. That is a semantic error in the reconstruction rather
than a codegen difference, and it is the reason those stores could never carry
the right register.

Correcting both to `gMemCard_nIOResult = r;` is right by the disassembly but
takes the build from 9 short to **11 short**, with the differing count
unchanged at 283. Removing the two `li` leaves nothing to replace them, so the
two instructions have to come back from the *shape* of the store rather than
its value.

**The shared-store shape was built and is inert.** The target reaches this store
from two arms by branch and from a third by fall-through that sets `2` in
`.L80044BA8`, so the source was rewritten as one labelled store fed by three
paths - `result = r; goto store_result;` in the two arms, `result = 2;` falling
into `store_result:` in the third, with the label placed exactly where
`.L80044BAC` sits. That is 286 - 11 short - and 283 differing, identical to
simply storing `r` in the two arms.

So the store's shape is not the missing two instructions either. Both the value
correction and the block structure are right by the disassembly and neither
changes the count, which means the deficit is somewhere the store is not. The
next attempt should re-derive the deficit from the multiset on the corrected
source.

**Re-derived, and the prediction was wrong:** `nop -6` and `sw -4` are
**unchanged**. They survive both corrections, so they were never about this
store's value or its block shape.

**What the four missing `sw` actually are.** Counting them out:

```
target      8 register saves (ra, s0-s6) + 5 gMemCard_nIOResult + 2 out-pointer = 15
candidate   7 register saves             + 2 gMemCard_nIOResult + 2            = 11
```

The deficit is one register save plus **three `gMemCard_nIOResult` stores**. The
target writes that global five times; this build writes it twice, because GCC
cross-jumps the identical `sw` / `j` / `nop` tails together.

**The target has three byte-identical three-instruction tails that GCC would
normally merge, and does not merge them.** Three of its five stores are
`sw $v0, %gp_rel(gMemCard_nIOResult)` followed by `j .L80044C8C` and a `nop`,
in separate blocks, differing only in the `addiu $v0,N` above them. `volatile`
does not explain it - volatile prevents reordering and elimination, not tail
merging, and this build merges them while declaring the same `volatile`.

That restates the whole residual as one question rather than three symptoms:
**three merges the target does not perform, worth six instructions, plus the
callee-saved register the unmerged form needs.** The `nop` deficit is not
separate, since each unmerged tail carries its own delay slot.

Anything that makes those three tails non-identical is worth measuring. The
register-gates-cross-jumping mechanism recorded for `Duel_LoadPackageStage` is
the obvious candidate, but all three already use `$v0`, so it would have to come
from the value's provenance rather than from a pin.

**`volatile` is inert on this global and can be dropped from the search.**
Building the stored source with `extern s32 gMemCard_nIOResult` instead of
`extern volatile s32` gives a byte-identical object: 286 instructions, 283
differing, the same five references in the assembly. So the qualifier is
neither causing nor preventing anything here, and the merge cannot be
controlled from the declaration.

That is worth stating because `volatile` is the reflex answer for "the target
keeps repeated accesses separate", and it is the right answer elsewhere in this
repository - `D_8009B0F4` in `Duel_LoadPackageStage` needs it. It is not the
answer here, and the difference is that volatile constrains *reordering and
elimination* of the accesses, while what differs here is *tail merging of
identical blocks*, which is a jump-optimisation pass that does not consult the
MEM's volatility.

### Levers that got it here

- *Both sub-state machines are switches, not if-chains.* The `beq` against 1,
  then `slti` against 2, then `beq` against 2 with a default jump is exactly a
  three-case `switch (D_8009B44F)` with case 0 falling through into case 1.
  Written as an if-chain the two tails do not cross-jump and the shared block
  at 0x800449DC never appears.
- *Case bodies must be written in the jump table's block order*, which here is
  1/2, then 11/12, then 3/4, then 8 - not numeric order. The table's targets
  are `0x800448E4`, `0x800448FC`, `0x800449B4`, `0x80044B70`.
- *The success path of the reopen loop has to be written before the loop's
  preheader*, reached only by `goto` from inside the loop. Retail's
  `bne $s1, $s2, .L80044C0C` is a backward branch; with the `close`/result-0
  block written inside the loop body it lands after the loop and 25
  instructions move.
- *`D_8009B43E` is a `u8` for the switch selector and an `s8` everywhere else.*
  The selector is `lbu`, `- 1`, then an 8-bit sign extension, so it is
  `(s8)(D_8009B43E - 1)` off a `u8` declaration; the terminating store is
  `addiu $v1, $zero, -1`, which needs an `s8` lvalue, spelled
  `*(s8 *)&D_8009B43E = -1;`.
- *The `_card_status`/`_card_wait` argument is `D_8009B437 != 0`*, not the byte
  itself - retail has the `sltu $a0, $zero, $a0`.
- The `open` mode for the read/write path is `0x8001` or `0x8002` selected by
  `D_8009B43E == 4`, and the commit reopen's mode is
  `(D_8009B434 << 16) | 0x200`.
