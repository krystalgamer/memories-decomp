The duel-field card-inspect handler, between `duel_field_guardian_compare.c`
and `duel_field_display_objects.c`. `duel_field_display_objects.c` already
declares it and calls it, so the prototype is fixed: a display source and a

clears the two inspect flags, and if the record is occupied reads its card id,

text box positioned from the source's display object.

### What the shape needed

- **The index parameter is `s32`, not `u8`.** The neighbouring header declares
  it `u8`, but retail multiplies it by 28 and takes `% 15` with no `andi`, so
  the definition takes a word. The `u8` spelling costs an entry mask.
- **`D_8009B344` is `volatile`.** Retail stores the masked nibble, reloads it,
  adds 23 and stores again; a plain `u8` lets GCC keep the value in a register
  and fold the two stores into one, which is three instructions short. The
  `volatile` spelling restores the store/reload/store and brings the build to
  the exact 210.
- **The `< 20` arm is the fall-through.** Retail branches to the high-class
  arm, so the source keeps `< 20` as the then arm.
- **`0x800A`-based globals are not `$gp`-relative.** `gcc_2_8_1_g0` is the
  family profile and puts nothing in small data.

- **Two more branch polarities.** Retail falls through to the `>= 5` arm of the
  `index % 15` test and to the `>= 20` arm above it, so both are written with
  the condition that makes the larger block the fall-through.
- **The side test compares `index >= 15`, not `index < 15`.** Retail emits
  `slti` followed by `xori ...,1` before the comparison, which is the extra
  instruction that spelling costs. Writing it as `(index < 15) != D_8009B1D5`
  is the same truth value and one instruction shorter, so it looks better on a
  diff while being the wrong source.

### What is left

One instruction and 196 positions, and both trace to the same allocation
difference. Retail spends four callee-saved registers — `$s0` for the record,
`$s1` for the index, `$s2` for the running text-box mode and `$s3` for the
source — and copies the record into `$a0` for the `Duel_CalcCardStats` call.
This build spends two, keeping only the mode and the source, and coalesces the
record straight into `$a0`, so the frame is 40 bytes against retail's 48 and
every register name downstream shifts.

The record and the index are read on both sides of that call in the
instruction stream, which is what should make GCC 2.8 treat them as crossing
it, but the blocks are mutually exclusive and this build's allocator does not.
Pinning all four to the retail registers overshoots by seven instructions.

Retail also keeps `D_800E9FF0` and `D_801D5608` in base registers and reaches
their fields with displacements, where this build materialises `D_800E9FF0`
through the assembler's `$at` macro and forms `&D_801D5608[2]` outright.
Staging both in locals changes which of the two is folded but not the count.

Neither register is live across a call on any path: the record's last use is
the `Duel_CalcCardStats` argument itself on the branch that calls, and its
other uses are on the mutually exclusive branch. Retail spends callee-saved
registers on them anyway, so this is an allocator preference rather than a
requirement, and no source form found so far reproduces it.
