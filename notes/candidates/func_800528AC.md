## `func_800528AC` at 0x800528AC

`gcc_2_8_1_g8_split`, 287 of 288 instructions, **opcode multiset distance 1**
(one `addu`), **279 differing positions** against the linked target.

*The two figures measure different things and the smaller one is misleading.*
This entry previously led with "16 non-relocation word mismatches", which counts
disagreements after ignoring relocated words. Compared position by position
against the linked bytes the figure is 279, and the reason is the missing
instruction: the build is one short, so everything from `+0x008` onward sits one
slot early. **The 279 is displacement, not disagreement** - the same shape as
`func_80018FEC`, where 114 positions came from one delay-slot decision.

### Retail materialises the base once, so the copy is a coalescing failure

Scanning retail's 288 instructions settles what the missing `addu` is and is
not. There is exactly **one** materialisation of `D_800F2B50`: a single
`lui $v0,0x800F` at `+0x004` and a single `%lo` immediate `0x2B50` at `+0x008`.
The `move $21,$2` at `+0x010` copies that one value into `$s5`.

So retail does **not** materialise the address twice, and the missing
instruction is not a second address computation. It is a register copy that
retail's allocator failed to coalesce away and ours does not emit at all,
because ours materialises straight into the callee-saved register.

That rules out the reading the section below tests. Both builds compute the
address once; the difference is only that retail computes it into `$v0` and then
copies, where this build computes it into `$s4` and is done. Sharing the
materialisation between the two source uses therefore cannot produce the missing
instruction - and measurably does not, since the variant that reaches 288
instructions is still one `addu` short and has gained an `addiu` elsewhere
instead.

The target is consequently narrow and awkward: reproduce a **coalescing failure**
rather than a computation. Nothing in the source asks for a redundant copy, which
is why naming the value twice does not help - GCC assigns both names the same
register precisely because it *can* coalesce them.

### Sharing the base supplies the count and not the instruction

The obvious reading of the section below - the address has two uses, so give
both a single materialisation - does produce the missing instruction's *count*
and is still wrong.

Deriving the closing block's address from `table` rather than from
`D_800F2B50`, and the same through a separate `base` variable, both reach
**288 of 288 instructions**, up from 287, and the positional figure falls from
279 to 234. But the opcode multiset goes from **distance 1 to distance 2**: the
build is still one `addu` short and is now one `addiu` long. It gained an
instruction of the wrong kind.

| candidate | insns | positions | distance |
| --- | --- | --- | --- |
| stored | 287/288 | 279 | **1** (one `addu` short) |
| both uses from `table` | 288/288 | 234 | 2 (one `addu` short, one `addiu` long) |
| the same through a `base` local | 288/288 | 234 | 2, identical |
| `base` pinned to `$v0` | 286/288 | 279 | two instructions short |

So this is the second candidate on this campaign that scores better and is
further away, after the interleaved read-backs rejected on `func_8002EE94`. The
rule that caught both is the same: the residue names the instruction that has to
appear, and a candidate that does not produce *that* instruction has not moved
toward retail however the count reads.

**What it does tell us** is that the two variables are coalesced. Retail's
`move $s5,$v0` needs the address to exist in a caller-saved register first and
then be copied into a callee-saved one; writing `base` and `table` as separate
variables does not achieve that, because GCC assigns them the same register and
the copy disappears. Whatever produces retail's shape has to keep both live at
once, and two names for one value do not.

### The missing instruction is the base pointer's copy

```
retail   lui $v0,%hi   addiu $v0,$v0,%lo   sw $s5,68($sp)   move $s5,$v0
build    lui $v0,%hi   sw $s4,64($sp)      addiu $s4,$v0,%lo
```

Retail materialises `D_800F2B50` **once into `$v0`** and then copies it into the
callee-saved register with `move $s5,$v0` - which is `addu $s5,$v0,$zero`, and is
exactly the one `addu` the multiset is short. The build folds the `%lo` add
straight into `$s4` and never makes the copy.

The likely cause is that the address has **two uses**: `table = D_800F2B50` near
the top and `(u8 *)D_800F2B50 + off + 1` in the closing block. Keeping the
materialised base in `$v0` is what lets both be derived from one `%hi`/`%lo`
pair, and that is the same mechanism already recorded for `D_800EB0F8` on
`func_8002EE94` - one high half reused by a second pointer.

So this entry is one instruction away in shape, and the 279 will collapse when
that instruction appears. It should be picked up on that basis rather than as a
large residual.

 Written from scratch: no stored candidate, no rows in
`external_attempts.csv`, empty inventory note.

The per-frame tint pass over the ten 0x18-byte requests at `D_800F2B50`, called
once from `func_80059CE4` in `model_cleanup.c`, between the three
`func_800540B4` slot draws and the `func_800556E8` calls. Each live request
holds a start colour, an end colour, an elapsed count and a duration; the
function interpolates the colour
for this frame into the model slot's `field_DC0`, redraws the slot through
`func_800540B4`, then puts back everything it touched and advances the request's
clock.

Per entry:

* bit 0 of the `u16` at `+0` is the live flag, bit 1 picks one of the two
  `D_800F2C40` slots (stride `MODEL_SLOT_SIZE`), bit 2 becomes `D_8009AF9B`
  around the draw, and bits 3 to 7 are the part id `v`.
* the slot must have `field_E1F` set, and
  `Model_HasInsufficientBufferSpace(side, entry->field_13)` must say there is
  room; either check failing skips straight to the clock update.
* `field_DC0`'s four bytes are saved to the stack, then rebuilt as
  `start[n] * (duration - elapsed) / duration + end[n] * elapsed / duration`
  for the three colour bytes with `field_13` in the fourth.
* two passes over `slot->field_E1B` parts call `func_8004DC38`. The first
  overwrites each part record's `+0xC` with `v` and passes the entry's
  `field_0A`; the second puts back the slot's own `field_BF5` and the
  `field_E06` captured before the draw. `field_1E0[j]` is the part pointer
  array, and both passes leave `slot->field_BF5` set to the value they used.
* `D_8009AF9C` gets `&D_800F2B50[i] + 1` and is cleared again straight after
  `func_800540B4`.
* the clock update runs on every live entry, including the two skip paths:
  `field_0C += func_80058E1C()`, and reaching `field_0E` clears the live bit.

## Five things the shape needed

**The base pointer has to go through a local, even though GCC folds it away
again.** Written `D_800F2B50[i].field`, GCC eliminates the loop counter: the
array giv's `add_val` is the symbol itself, which is exactly the case
`maybe_eliminate_biv_1` rewrites, so the loop test becomes
`slt $sN, D_800F2B50+240` and the `slti $v0, $t3, 0xA` on `i` disappears along
with its stack slot. Assigning `table = D_800F2B50;` first and indexing
`table[i]` leaves `i` alive with both it and the byte offset spilled, which is
what retail does - and the final code is identical either way, because the
pointer is constant-folded back into the address before it is emitted. Without
it the build comes out at 292 instructions against 288 rather than 287; it is
the single most load-bearing line here.

**The record pointer must be array-indexed, not walked.** `e = &table[i]`
gives one giv with every field offset folded into it (`0x0`, `0xA`, `0xC`,
`0xE`, `0x10` to `0x16`), which is retail's `$s5`. Walking it as a biv
(`e++` in the increment clause) makes GCC strength-reduce the field addresses
into a *second* pointer at `e + 14` used with offsets -4, -2, 0 and 5, plus its
own increment and its own callee-saved save and restore.

**The first test is a byte load.** `(e->flags & 1) == 0` written against the
`u16` shares one `lhu` with the `(e->flags >> 1) & 1` that follows it. Retail
has `lbu $v0, 0x0($s5)` and then a separate `lhu` at the same address, which is
what `(*(u8 *)e & 1) == 0` produces: the narrowed load is a different mode, so
CSE cannot merge the two. That is one instruction - the difference between
sharing a single `lhu` and issuing both loads - and it was the first residual
found.

**The flags word and the part id are one variable.** Retail's `$s2` is loaded
by `lhu`, shifted in place by `srl $s2, $s2, 3`, and masked in place by
`andi $s2, $s2, 0x1F` in a delay slot 0x94 bytes later. Writing
`v = e->flags; side = (v >> 1) & 1; v = (v >> 3) & 0x1F;` with `v` unsigned
reproduces all three; `u32` matters, since an `s32` gives `sra`.

**The two inner loops need separate counters and explicit `s32` copies of
their `u16` fourth arguments.** Retail hoists both `zero_extend`s out of the
inner loops - `andi $s3, $s3, 0xFFFF` for `field_0A` and
`lhu $s2, 0x24($sp)` for the saved `field_E06`, each once, in the preheader -
and GCC will not do it on its own here, so the conversions are written as
`aa = a;` and `sv = sav06;` before the loops. Reusing one `j` for both loops
also costs two instructions' worth of register naming: retail's first loop has
the counter in `$s1` and the part pointer in `$s0`, and its second loop has
them the other way round, which only happens with two distinct counters.

## What is left is one instruction

The residual is the giv initialiser. Retail materialises the table address into
a scratch register and copies it:

```
lui   $v0, %hi(D_800F2B50)
addiu $v0, $v0, %lo(D_800F2B50)
addu  $s5, $v0, $zero
```

which is `emit_iv_add_mult` reaching `emit_move_insn (giv_reg, add_val)` with
`add_val` still a `REG` - the pointer local surviving as its own pseudo through
`strength_reduce` and past `combine`. Every build here expands the address
straight into the giv register instead:

```
lui   $v0, %hi(D_800F2B50)
addiu $s5, $v0, %lo(D_800F2B50)
```

Nothing tried keeps the copy: eight spellings of the initialiser
(`&D_800F2B50[0]`, `D_800F2B50 + 0`, `(Record *)(s32)D_800F2B50`, an initialiser
on the declaration, `Record *const`, `register`, a `u8 *` base with
`((Record *)base)[i]`, and an `s32` base with `(Record *)(base + i * 0x18)`),
assigning `table` inside the loop so `move_movables` hoists it, a `goto`/label
barrier before the loop to break CSE's constant equivalence, a second
`u8 *base` local for the `D_8009AF9C` expression, and routing the
`D_8009AF9C` expression through `table` so the pointer has two uses. That last
one does reach 288 instructions, but by adding an `addiu $v0, $v0, 1` in the
loop rather than the copy in the prologue - the `+ 1` only folds into
`%lo(D_800F2B50 + 0x1)` when the expression is written against the symbol.

Everything downstream of that one instruction follows from it: retail's scratch
registers sit one higher than this build's (`$t1` and `$t2` where this has `$v0`
and `$t1`), because the surviving pointer pseudo shifts the allocation order.
Fifteen of the sixteen remaining mismatches are that renumbering.

## The missing `addu` is `emit_iv_add_mult`, and the condition is exact

The entry above says the target is a coalescing failure and that nothing in the
source asks for a redundant copy. Both are true, but they describe the problem
from the outside. Reading GCC 2.8.1's own sources turns it into a condition that
can be checked rather than guessed at.

Retail and this build agree for one instruction and then split:

```
retail   lui   v0,%hi(D_800F2B50)   build   lui   v0,%hi(D_800F2B50)
         addiu v0,v0,%lo(...)               addiu s4,v0,%lo(...)
         move  s5,v0
```

Both materialise the address into `$v0`. The only difference is whether the
`%lo` add writes to the destination or to the temp with a copy after it.

That copy is emitted in `loop.c`:

```c
result = expand_mult_add (b, reg, m, a, GET_MODE (reg), 0);
if (reg != result)
  emit_move_insn (reg, result);
```

`b` is the biv's initial value (0), `m` the multiplier (24), `a` the giv's
`add_val`, `reg` the destination. `expand_mult_add` folds `0 * 24 + a` down to
`a` and calls `expand_expr (a_tree, target=reg, ...)`. The chain that decides
everything is `make_tree`: for anything that is not arithmetic it returns an
`RTL_EXPR` wrapping the rtx unchanged (`expmed.c`, default case), and
`expand_expr` of an `RTL_EXPR` returns `RTL_EXPR_RTL` **verbatim, ignoring the
target**. So `result` is the `add_val` rtx itself, `reg != result` always holds,
and `emit_move_insn (reg, result)` is what actually emits the initialiser.

The two outcomes are then just two spellings of that move:

- `add_val` is a **`SYMBOL_REF`**: `emit_move_insn (reg, symbol)` is `la reg,sym`,
  which MASPSX expands to `lui`/`addiu` **into `reg`**. Two instructions, no copy.
  This is what this build does.
- `add_val` is a **`REG`**: the address is materialised into that pseudo first and
  the move is register-to-register - `addu $s5,$v0,$zero`, printed `move`. Three
  instructions. This is retail, and it is the missing `addu`.

**So the target is not "make the allocator fail to coalesce". It is "make the
giv's `add_val` be a REG rather than a `SYMBOL_REF` at loop time".** That is a
property of the RTL reaching the loop pass, and `simplify_giv_expr` preserves it:
for any invariant that is not a `CONST_INT` it returns `gen_rtx (USE, mode, x)`,
carrying whichever rtx it was given. The distinction survives to `emit_iv_add_mult`
untouched.

### Four axes closed against that condition

Each of these was measured against the 287/288, distance 1 base.

| axis | result |
| --- | --- |
| `-fforce-addr` | byte-identical to the base |
| all 30 GCC 2.8.1 profiles, two bases | nothing beats distance 1 |
| more uses, to make CSE keep a register | distance 2 at best |
| assigning the base inside the loop | identical to the base |

**`-fforce-addr` is the interesting negative.** `expr.c` has exactly the wanted
transformation - `if (flag_force_addr && GET_CODE (op0) != REG) op0 = force_reg
(Pmode, op0);` - which turns an address into a REG. It changes nothing here
because it sits on the `ADDR_EXPR` path, and the giv initialiser never takes that
path: it arrives as an rtx through `make_tree` and leaves as an `RTL_EXPR`. A flag
that does the right thing in the wrong pass is worth recording, because the name
makes it look like the answer.

The profile sweep covered all 30 GCC 2.8.1 profiles against both the base and the
best alternative, including `no_cse_follow_jumps` and `no_strength_reduce`, which
touch the passes involved. The best non-base results were distance 2 and 3.

For CSE pressure the reasoning was that CSE keeps an address in a register when
there are enough uses to pay for it, so the base was given more uses: routing the
second reference (`D_8009AF9C = (s32)((u8 *)D_800F2B50 + off + 1)`) through the
local, and replacing all fourteen `e->` accesses with `table[i].`. Neither works.
Reading the assembly says why: with the local used twice, GCC still re-expands
`lui %hi`/`addiu %lo` into a fresh temp at the second use rather than reusing the
register, so the local never becomes the thing the RTL refers to.

### The exact instruction count is not progress

Routing the second reference through the local reaches **288 of 288
instructions**, against the base's 287. It is a worse candidate: distance 2 rather
than 1, because it supplies the count with a surplus `addiu` in the loop while
still lacking the `addu` in the prologue. The count and the multiset disagree, and
the multiset is right - this is the same trap as the offset-induction forms above,
which halve the position count while multiplying the distance by five.

## Reading the loop as a whole, rather than forcing a register

The section above ends by naming a compiler-internal target: make the giv's
`add_val` a REG. That is a correct reading of the mechanism and a poor guide to
what to write, because it invites forcing values into registers rather than
asking what source produces the shape. Reading retail's loop end to end gives a
better frame and closes more ground.

### What retail's loop actually is

```
+0x42C  addiu s5,s5,24     element pointer
+0x430  lw    t2,40(sp)    byte offset, on the stack
+0x434  lw    t3,32(sp)    counter, on the stack
+0x438  addiu t2,t2,24
+0x43C  addiu t3,t3,1
+0x440  slti  v0,t3,10
+0x444  sw    t2,40(sp)
+0x448  bnez  v0,0x800528ec
```

Three induction variables: an element pointer in a register, and a byte offset
and a counter **both living on the stack**, initialised by the prologue's
`sw zero,32(sp)` and `sw zero,40(sp)`. All element fields are constant
displacements from `$s5` (`0`, `10`, `12`, `14`, `16`..`22`), and `$s4` is a
separate slot pointer into `D_800F2C40` (`3590`, `3061`, `3611`). The function has
one epilogue, at +0x450.

That confirms the source shape already in the entry - both a counter and a byte
offset, with the record array-indexed - and it explains an earlier negative:
driving the loop from the offset alone reaches 282 instructions and distance 10
precisely because retail keeps the counter as a third induction variable.

### The body is already exact

Retail computes the `D_8009AF9C` value as

```
lui   t1,0x800f          addiu t1,t1,11089        (D_800F2B50 + 1)
lw    t0,40(sp)          addu  v1,t0,t1
```

folding the `+ 1` into the address constant and rematerialising the base inside
the loop rather than keeping it live. This build emits the same five instructions
with the same association, `%hi(D_800F2B50+1)` and `%lo(D_800F2B50+1)`. So the
second reference is right, the base is *supposed* to be rematerialised, and the
prologue temp is not a live base being shared - it is used once and dead.

### The initialiser has three possible shapes and retail's is the third

| | form | emitted |
| --- | --- | --- |
| split profiles | `lui tmp,%hi` then `addiu dest,tmp,%lo` | 2 insns, no copy |
| no-split profiles | `la dest,sym` | 2 insns, no copy |
| **retail** | `lui tmp,%hi`, `addiu tmp,tmp,%lo`, `move dest,tmp` | **3 insns** |

Both compiler-produced shapes write the address into the destination. Retail's
completes it in a temp and copies. Checking the no-split profiles was worth doing
and is a negative: they produce retail's *two-halves-in-one-register* pattern but
into the destination, so they still have no copy, and they cost 289 instructions
against retail's 288.

The distinction is therefore not split versus no-split, and not which register
anything lands in. It is that retail's address is materialised **as a value in
its own right** and then assigned, which is what `force_reg` followed by an
assignment produces, and which no plain initialiser spelling has yet reproduced.

### Further axes closed, none of them by pinning

| axis | variants | result |
| --- | --- | --- |
| declaration order | 6 permutations of the local block | all identical to the base |
| plain `register` on the pointers | `e`, `table`, both, `slot` | all identical to the base |
| whole-function source readings | shared `u8 *` base; base-derived element pointer; walked pointer in the `for` init; walked pointer from a base local | distance 2, 4, 8, 9 |

Declaration order being completely inert is worth recording on its own, since
pseudo numbering follows it and it is a natural thing to suspect when two builds
allocate the same nine callee-saved registers in a different order. It does not
move this function at all.

## Retraction: the copy is emitted, and a later pass deletes it

The `emit_iv_add_mult` section above is **wrong**, and the way it is wrong is
worth keeping rather than quietly deleting. It concluded that the copy appears
only when the giv's `add_val` is a REG, that this build's `add_val` is the
`SYMBOL_REF`, and that the task was to change that. Every step of the reasoning
about GCC's sources is accurate. The premise about *this build* is false.

GCC 2.8.1 will dump RTL per pass, and asking it is decisive where reading
`loop.c` was not. From the loop dump:

```
Insn 32: giv reg 95 src reg 80 benefit 8 used 1 lifetime 187
         replaceable mult 24 add (reg/v:SI 96)

(insn 525 519 15 (set (reg:SI 258)
        (reg/v:SI 96)) -1 (nil))
```

`add_val` is `(reg/v:SI 96)` - already a REG, the pseudo for `table`, exactly as
retail requires. And insn 525 **is the copy**. GCC emits it. The condition the
section above set out to satisfy was satisfied all along.

So the copy is not missing because it was never created. It is created and then
removed, and the dumps say by which pass:

Comparing the *content* of insn 525 across dumps, rather than merely whether an
insn with that number exists, names the pass:

| dump | insn 525 |
| --- | --- |
| `.loop` | `(set (reg:SI 258) (reg/v:SI 96))` - the copy |
| `.combine` | `(set (reg:SI 258) (lo_sum:SI (reg:SI 97) (symbol_ref "D_800F2B50")))` |
| `.lreg` | unchanged from `.combine` |

**The instruction combiner removes it.** `table` is defined once by
`reg96 = lo_sum (reg97, D_800F2B50)`, and insn 525 is its only use, at which it
dies. That is exactly the two-insn pattern `combine` exists to fold: it
substitutes the definition into the use, producing `reg258 = lo_sum (reg97, sym)`
and leaving `reg96` dead. The result is this build's `lui` into a temp followed by
`addiu` into the giv register - one instruction where retail has two.

So the sequence is: the copy is emitted by `emit_iv_add_mult`, and combine folds
the address computation through it. Nothing about allocation is involved, and
retail's `$v0`/`$s5` pair is the *consequence* of the copy surviving rather than
its cause.

This relocates the target precisely: `table` must not be a
single-use pseudo that dies at the copy, because that is the exact shape combine
folds. It also
explains why routing the second reference through the local gets the instruction
count exactly right but the wrong instruction: GCC rematerialises the address at
that second use rather than holding `table` in a register, so the live range still
ends at insn 525 and the copy is still coalesced away. The surplus `addiu` is that
rematerialisation's `%lo`.

**Method note.** Three sections of this entry were written by reading compiler
sources and reasoning forward about what they would do. One RTL dump falsified
the conclusion in a single command. Reading the source establishes what a pass
*can* do; only the dump establishes what it *did*.

### The overlap cannot be created from the source, and that is measurable

The retraction above relocates the target to "make `table` live past insn 525 so
the two ranges conflict". That direction is also closed, and by a positive control
rather than an argument.

The control adds a use of `table` *after* the loop - semantically wrong, but it is
a probe, and if a second use were enough it would keep the definition alive. It
does not.
The build grows to 290 instructions and the prologue is unchanged:

```
lui   s4,%hi(D_800F2B50)
addiu s4,s4,%lo(D_800F2B50)
```

GCC rematerialises the address at the later use instead of holding it, so
`table`'s range still ends at insn 525 and the copy is still deleted. That is the
same behaviour seen at the in-loop second reference, and the reason is the same:
a split address costs two instructions to rebuild, while holding it across the
loop costs a callee-saved register across seven calls. Rebuilding always wins.

So adding uses does not stop the fold, in the loop or after it, because each extra
use is satisfied by a fresh rematerialisation rather than by the original pseudo.
Combined with the retraction, the position is sharper than it looks:

- the copy **is** emitted, so nothing about the expansion needs changing;
- it is folded away by combine, which substitutes `table`'s
  `lo_sum` definition into its single use;
- and no source-level use of `table` prevents that, because GCC would rather
  rematerialise the address at the extra use than keep the value, which leaves
  the original definition single-use exactly as before.

Whatever retail did, it did not do it by giving `table` another use. The remaining
possibilities are that retail's giv initialiser has a non-constant `b`
(`bl->initial_value`), or that the pseudo `$v0` holds something whose origin is
not a rematerialisable constant address at all.

### A positive control that works, and what it costs

Combine folds the copy because `table` is a single-use pseudo that dies at insn
525. That predicts a lever: give `table` a second use *in the same basic block*,
and the definition can no longer be substituted away.

The probe adds `D_8009AF9C = (s32)table;` immediately after the assignment -
semantically wrong, but it tests the prediction. The copy appears:

```
build    lui v1,%hi   addiu v1,v1,%lo   sw s4,64(sp)   move s4,v1
retail   lui v0,%hi   addiu v0,v0,%lo   sw s5,68(sp)   move s5,v0
```

Structurally identical, differing only in which registers the allocator chose,
and from `+0x014` onward the two builds agree instruction for instruction where
before they were displaced. This is the first positive control on this function
that behaves as predicted, and it confirms the combine account.

It is not a candidate: the probe's store is a real instruction, so the build is
289 against retail's 288. The remaining problem is therefore precise and small -
**find a second use of the base that costs nothing**, or a construct that
separates the definition from the copy without adding an instruction.

Two observations bound the search. Every use *inside* the loop is satisfied by a
fresh rematerialisation rather than by the original pseudo, which is why routing
the in-loop reference through the local leaves the fold intact; the same is true
of a use placed after the loop. And retail's own pre-loop code is only the address
materialisation, the copy, and the two `sw zero` stores that initialise the
counter and offset - so whatever kept retail's definition from being folded is
either not a second use at all, or is one that leaves no trace of its own.

## The copy is reproducible, and the criterion is a *live* second use

The combine account said `table` must not be a single-use pseudo dying at the
copy. A variant now reproduces retail's prologue outright, which pins the
criterion down further and prices it.

Moving the element-pointer assignment into the loop condition:

```c
for (i = 0, off = 0; e = &table[i], i < 10; i++, off += 0x18) {
```

gives

```
        build                    retail
+0x004  lui   v0,%hi            lui   v0,%hi        agree
+0x008  addiu v0,v0,%lo         addiu v0,v0,%lo     agree
+0x00C  sw    s4,64(sp)         sw    s5,68(sp)
+0x010  move  s4,v0             move  s5,v0         the missing addu
```

The first three instructions agree exactly and **the copy is present**, differing
from retail only in which registers the allocator picked. The RTL confirms the
mechanism rather than a coincidence: in `.combine` the insn is still
`(set (reg:SI 267) (reg/v:SI 96))`, untouched, where the base build has already
folded it to a `lo_sum`.

### Live uses, not uses

Counting references to `reg96` in the loop dump is misleading, and the correction
matters. The base build *does* contain a second reference,
`(insn 32 (set (reg/v:SI 95) (plus:SI (reg/v:SI 96) (reg:SI 102))))` - the
original, un-reduced giv computation. It is dead once strength reduction
rewrites the uses to the reduced register, so flow deletes it before combine
runs, leaving one use and permitting the fold.

The condition-placed variant keeps several of those computations **live**: its
loop summary lists a single giv where the base lists seven, all reduced to one
register. So the criterion is a *live* use at combine time, and the same change
that supplies one also suppresses the strength reduction that would have removed
it. Those un-reduced computations are exactly the variant's four extra
instructions - one surplus `addu` beyond the copy, one `lw`, two `sw`.

A dead use supplies nothing, which is directly measurable: adding
`sv = (s32)table;` to twelve different variants changes the output of **none** of
them.

### What every route to the copy has cost so far

| route | insns | distance | copy |
| --- | --- | --- | --- |
| base | 287 | **1** | no |
| second use in the preheader (probe) | 289 | - | yes |
| assignment in the loop condition | 292 | 4 | yes |
| second reference through the local | 288 | 2 | no |
| use after the loop (probe) | 290 | - | no |

Retail is 288 with the copy. Every variant that produces the copy overshoots, and
every variant that reaches 288 lacks it. The 288-instruction one is worth stating
precisely, because it is the near miss: routing the in-loop reference through the
local materialises the base only once and reaches the exact count, but spends the
instruction on an `addiu` for the `+ 1` - which no longer folds into the address
constant once the base is a register - while `la` still writes straight into the
giv register. Three spellings of that association (`+ (off + 1)`,
`&((u8 *)table)[off + 1]`, `(... + off) + 1`) are canonicalised to the same
output.

A systematic grid over four axes - where the element pointer is assigned (body,
condition, `for`-init with `e++`), how the second reference is spelled (symbol,
local, element pointer, offset-cancelled), and whether a dead use is added -
produces 24 variants, and none beats the base's distance of 1.
