## `func_80045334` at 0x80045334

`gcc_2_8_1_g0`, 70 of 70 instructions, 2 differing positions.

The instruction mix is exact and every register agrees. What is left is a
scheduler tie-break between two independent stack stores: the target writes
`f04` at `0xCC` and puts `f08` in the `jal` delay slot, and this build does the
reverse.

`gcc_2_8_1_g0_no_sched2` reads the order out directly, and it is the fact that
matters here: the natural store order is `f08`, `f0C`, `f04` -- `kind`,
`second`, `first` -- and the target needs `f04`, `f0C`, `f08`. Everything else
in the function, including `addiu $a0, $sp, 0x10` at `0xC0`, is already
correct on this base.

**The pass responsible is now identified, and it is `sched2`.** The RTL dumps
place the reorder exactly: `combine` still holds the source order
`sp+20, sp+24, sp+28`, and `sched` (sched1) rewrites it to `24, 28, 20`, which
`greg` and `sched2` then carry through. So the reorder is a scheduling decision,
not an allocation or lowering one.

That is only half of it, and the other half is why the obvious lever fails.
`-fno-schedule-insns` does stop sched1 -- with it, `greg` keeps the source order
`20, 24, 28` -- but `sched2` then reorders them again on its own, so the emitted
order still is not the source order. Ordering the source as `f04`, `f0C`, `f08`
(the shape the target implies) under `-fno-schedule-insns` lands at 3, emitting
`28, 24` with `20` in the delay slot. And `sched2` cannot simply be turned off:
`-fno-schedule-insns2`, with or without sched1, builds **71 instructions against
70** on all six statement orders, so it is paying for the order with an extra
instruction elsewhere.

What that leaves is narrow and worth stating precisely: the target needs
`sched2` enabled *and* its tie-break among the three stores to come out
`20, 28, 24`. All three are equal-priority, all three kill their source register,
so nothing in the cost model separates them -- which is consistent with
statement order having no effect. The next attempt needs something that changes
the dependency height of one of these three values, not where its store is
written.

Also crossed since, none better than 2: all six permutations of the three store
statements (2, 2, 2, 3, 3, 3); `volatile` on single fields and pairs combined
with the reordered source (3 to 6); explicit register pins for `second` on `$17`
and `kind` on `$18` matching the allocation the target already uses (2, no
change), and swapping `first` and `kind` between `$16` and `$18` (6).

Attempts to make the three stores look dependent on each other, so the
scheduler would have to keep them in source order, also fail: the three fields
as an `s32 w[3]` array addressed by constant index (2 and 3, depending on
order) and the stores written through a byte-pointer view of `&req` (3). GCC
folds all of these back to `sp` plus a constant offset and disambiguates them
exactly as it does the struct members, so none of them creates the dependency.

The statement-order axis is now closed on both scheduler settings, not just
one. All six permutations were built again under `-fno-schedule-insns`, and
they land on the same 2 and 3 as with sched1 enabled. So `sched2` re-derives
this order from the dependency graph rather than carrying its input order
through: with sched1 on it keeps sched1's `24, 28, 20`, and with sched1 off it
turns the source order `20, 24, 28` into `28, 24, 20`. Neither is the target's
`20, 28, 24`, and no source order reaches it on either setting.

The emitted order is descending by the register holding the stored value --
`$s2, $s1, $s0` -- where the target is ascending, `$s0, $s1, $s2`. Forcing the
registers the other way round does reverse the emission, but then the registers
themselves are wrong: pinning `first` to `$18` and `kind` to `$16` lands at 6,
trading two wrong positions for three wrong registers. The target uses the same
allocation this build already has, so the register assignment is not the lever
either.

**The order half is now solved, on both functions.** The missing case in the
`volatile` sweep above was all three fields at once. Singles and pairs do not
work because `volatile` is not a barrier for non-volatile stores in this
scheduler -- a plain store hops straight over two volatile ones -- so only
volatile-versus-volatile is ordered and nothing short of all three constrains
the triple. With all three marked, and written in the target's order,
`sched2` emits `sw $s0, 0x14`, `sw $s1, 0x1C`, `sw $s2, 0x18`: the target's
order exactly, with no register, provenance or allocation change anywhere else.
Measured on this entry and on `func_80045208`'s, both at `gcc_2_8_1_g0`.

This does not need the dependency height of any value changed, which is what
the paragraph above asked for. It makes the three stores mutually ordered
instead, so the tie-break never runs.

What it costs is the delay slot, and that is now the whole residual: `dbr` will
not move a volatile store into the `jal` slot, so `addiu $a0, $sp, 0x10` takes
it and the five-store block shifts one position earlier. Six words differ
rather than two, but they are six words of *offset* with the order correct,
where the two were the order itself. A volatile store will sit in the middle of
the block quite happily -- with only `f08` volatile the emitted order is `f0C`,
`f08`, `f04` -- so the refusal is specific to the delay slot.

Placement table on `func_80045208`, differing words: `f08` alone 3, `f0C` alone
3, `f04` alone 6, `f04`+`f0C` 4, `f04`+`f08` 5, `f0C`+`f08` 3, all three 6,
against a base of 2. Nothing beats the base on count; the all-three form is
worth recording for which difference it leaves, not for its score.

Note the same two positions are the whole residual on the twin
`func_80045208` as well, so this tie-break is worth solving once for both.

That natural order is invariant. About 1800 variants were compiled crossing
assignment order, local declaration order, `volatile` subsets, the lvalue
spelling of each store (member, through a `struct Request *`, and through a
cast address), named local against inline expression for `first` and `second`,
register pins on `first`, `second` and `kind`, the position of `kind` within
each switch arm, and every profile. None moved it off `f04`/`f08` swapped, so
statement order is not the input the order is computed from.

`volatile` is the one control that does reach it, and it is worth knowing as a
lever rather than as a failed experiment: marking the fields `volatile` makes
the emitted store order exactly the source order. It cannot finish the job
here because a `volatile` store may not sink into the `jal` delay slot, so the
last store stays put and `addiu $a0, $sp, 0x10` takes the slot instead. All
three `volatile` lands at 5, not the 6 recorded previously; `f04`+`f0C`
`volatile` with the source ordered `f04`, `f0C`, `f08` -- the shape the target
implies -- lands at 4. So the remaining move is something that orders these
two stores without making the third one immovable.

Three register pins are needed and each corrects an allocation on a sequence
that is already exact: the `g_SDValue` pointer to `$a1` (unpinned it goes to a
callee-saved register and shifts everything), the table pointer to `$v0`, and
the request code to `$s3`. Two source-level facts also matter and are not
pins: the three-way test on `arg0 & 0xF000` is a `switch`, not an `if`/`else if`
chain -- the chain builds 67 instructions with `bne` where the target has `beq`
plus a `j` to the default -- and the default arm reads `code += 0x6000` rather
than `code = arg0 + 0x6000`, which is what keeps `$s3` live across it.
