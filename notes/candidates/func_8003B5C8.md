## `func_8003B5C8` at 0x8003B5C8

`gcc_2_8_1_g0_split`, 58 of 57 instructions, opcode distance 1, one extra
instruction and nothing else.

The function copies a 20-byte table out of `D_80010330` into a local buffer,
then walks it as ten big-endian `u16` keys. For each key it searches the
4-byte-stride table at `D_801D9004` (key in the low halfword, a zero word
terminating) and writes the 1-based match index into `D_800EAFF8`. The search
is skipped when the table's first word is zero, and that word is read once
before the loop rather than per iteration.

Six canonical attempts had gone terminal with no post-terminal work recorded.
This reaches an exact instruction sequence except for **one** instruction: the
build emits `lui $v0, %hi(D_801D9004)` followed by `move $t2, $v0`, where the
target has `lui $t2, %hi(D_801D9004)` and no copy. Drop that one instruction
from the build and every remaining differing word is a `%hi`/`%lo` immediate
or a branch target left unresolved in the object file, which link identically,
so the copy is the entire difference.

**What the shape needed.** Five things, none of them obvious from the
disassembly:

- *The outer loop compares signed integers, not pointers.* The target ends
  with `slt $v0, $a3, $t4` on two values that are plainly addresses, and this
  GCC emits `sltu` for any pointer comparison written in C. Nor is it biv
  elimination: probes across index loops with and without the inner search, a
  hoisted base pointer and the block copy all keep the index compare. The
  walking value and its bound have to be `s32`.
- *The inner search must be a `goto` loop.* Written as `do { ... } while`, the
  loop optimiser rotates it, puts the `e++` in a branch delay slot and then
  needs an `addiu $a0, $a0, -4` to undo it on the match path. The `goto` form
  is not marked as a loop for that pass, and the emitted shape is then the
  target's: an explicit `j` out with the store in its delay slot, and the
  advance at the top of the continue path.
- *`e` and `n` are initialised before the guard, not inside it.* Inside the
  `if` they are emitted after the key is computed; hoisted above it they land
  where the target has them, which realigns the whole loop head.
- *The store goes through its own pointer captured inside the guard.* That is
  what produces the target's `addu $a2, $t1, $zero`. Without it the store uses
  the walking output pointer directly and that copy is missing.
- *The 20-byte copy is a struct assignment of a byte array, and it has to be.*
  The target moves the block with five `lwl`/`lwr` and `swl`/`swr` pairs rather
  than aligned word moves, because the source is a byte array and GCC cannot
  assume word alignment for it. Wrapping the bytes in a `struct { u8 b[20]; }`
  and assigning the struct reproduces the block exactly; a `u32` view of the
  same storage does not. (This is #1725's finding, folded in here at
  krystalgamer's request when that PR was closed in favour of this entry. The
  signed outer-loop comparison above was derived independently in both, which
  is good evidence the lever is general -- #1725 measured it as distance 7 to
  5 from a different starting shape.)

With all five, every register in the function matches the target: `$t1` the
output pointer, `$t0` the odd index, `$a3` the buffer pointer, `$t4` the
bound, `$t2` the hoisted high part, `$t3` the guard word, `$a2` the store
pointer, `$a0` the search pointer, `$a1` the counter.

**The one extra instruction is a compiler artifact and it reproduces in six
lines.** The RTL dumps show the loop pass hoisting a second
`(high (symbol_ref "D_801D9004"))` out of the loop as a new pseudo, `cse2`
then rewriting that to a copy of the setup's pseudo, and the allocator failing
to coalesce the two even though the source dies at the copy. A minimal
function -- read a global once before a loop, take its address inside the loop
-- produces the identical `lui`/`move` pair under `-msplit-addresses`:

```c
extern u32 T[]; extern u16 OUT[];
void p1(void) {
    u32 first = T[0]; u32 *e; s32 i, n;
    for (i = 0; i < 10; i++) {
        e = T; n = 1;
        if (first) { while (*e) { e++; n++; } }
        OUT[i] = n;
    }
}
```

So the next attempt should be aimed at that coalescing, not at the loop.
Reading a different element (`T[1]`) removes the copy but costs a second
`lui`, which is the same instruction count. Crossed without removing it: five
placements of the guard read, the table base hoisted into a local (the loop
then emits `move` instead of the low-part add and the setup grows by one), the
table declared as a scalar with its address taken, the read spelled
`*(u32 *)D_801D9004` and `*e` after assigning `e`, fourteen permutations of
the six setup statements, `while`/`for`/`goto` forms of the outer loop, the
store as a direct `D_800EAFF8[k]` index instead of a pointer, and all eighteen
viable profiles.
