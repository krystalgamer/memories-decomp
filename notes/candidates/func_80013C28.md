## `func_80013C28` at 0x80013C28

`gcc_2_8_1_g8_split`, 283 instructions against a target of 286, **opcode
multiset distance 3**, 180 differing words unshifted. Written from scratch: no
stored candidate, no rows in `external_attempts.csv`, empty inventory note.

The `DsStartReadySystem` sector callback, registered from `func_800140A0` in
`file_cd_transfer.c`, which already declares it as
`func_80013C28(u8, u8 *, u32 *)`. It counts the event in `D_8009B114`, ignores
everything but event 1, then dispatches on the transfer descriptor's mode byte
at `D_8009AF18 + 0x46`:

* **mode 1** copies a 0x800-byte sector into `descriptor->field_08` - through
  `CdGetSector` normally, or word by word out of `D_8009B0F8` when bit
  0x40000000 of `D_8009B0F4` is set - and advances `field_08`. Bit 0x200000
  skips the copy entirely.
* **mode 2** picks the destination from `field_08` or `field_0C` by bit 0 of
  the `field_44` counter, copies the sector the same way, then stages the two
  halfwords at `+0x30`/`+0x32` into `+0x00`/`+0x02` and spins on `LoadImage2`.
  Bit 0x20000 advances `+0x30` by 0x40; otherwise `+0x32` steps by 0x10 and
  wraps into a `0x100` toggle with `+0x30` advancing on the wrap.
* **mode 3** clamps the sector length to `field_28`, copies `n / 4` words, then
  hands the block to the SPU through `SpuSetTransferStartAddr` and
  `func_80077150` and advances `+0x30` by `n`.

All three then decrement `+0x10` by 0x800, call `DsEndReadySystem` and
`CdReadyCallback(0)` when it runs out, decrement `+0x28` by 0x800 and fire the
descriptor's `+0x20` callback with a post-incremented `+0x40` sequence number
when *that* runs out. Modes 2 and 3 share that block and the `field_44`
increment after it; mode 1 has its own copy without the increment, which is why
it is written out separately rather than reached by `goto`.

## What the shape needed

**Each copy loop needs its own walking pointer.** In modes 2 and 3 the
destination is used again after the loop - by `LoadImage2` and by
`func_80077150` - so retail keeps it in `$s0` and walks a copy in `$a0`.
Walking the destination itself is both wrong and one instruction short per
loop.

**Mode 1's loop re-reads `descriptor->field_08` every iteration**, because the
store through it may alias the pointer field. Writing the destination as
`*(u32 *)(*(u8 **)(t + 8) + i * 4)` reproduces that; a local pointer hoists the
load out.

**The short-lived descriptor reads need their own locals.** Reusing one
function-scope pointer for the mode-2 halfword staging, the `+0x32` wrap and
the `field_44` increment merges those live ranges into the one that crosses the
indirect call, so gcc takes a third callee-saved register where retail uses two.

**Mode 3's `n / 4` is recomputed on every iteration of the loop test.** The
loop is written `while (i < n / 4)` and gcc leaves the `bgez`/`addiu 3`/`sra 2`
sequence inside, which is what retail has.

## What is left is three instructions, all one class

Retail keeps three register-to-register copies that this build coalesces away:

* `addu $a3, $a0, $zero` before mode 1's loop, because retail holds the
  descriptor in `$a0` and needs `$a0` as the load temp. Forcing it with a
  second local recovers this one, and it is already in the stored source.
* `lw $v1, 0x20($s0)` in each of the two callback blocks - retail re-reads the
  callback pointer for the call after having tested it, where this build reuses
  the tested value. The intervening store is to `+0x40` off the same base, so
  gcc disambiguates it and the CSE stands. Marking the call's read `volatile`
  does restore both loads, but then the argument copy `addu $a1, $v0, $zero`
  coalesces away in both blocks instead, so the distance stays at 3.

Crossed without improving: `u8`, `s32` and three-parameter forms of the event
argument (retail masks it into `$a1` and this build masks it in place in `$a0`,
which is what decides whether mode 1's loop needs its copy); reading the
sequence number through a re-materialised `D_8009AF18`; and the post-increment
spelling of the `+0x40` update.
