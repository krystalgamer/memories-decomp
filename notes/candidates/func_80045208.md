## What changed

**The three early `return 0` statements are one trailing `return 0` reached by
nested `if`s.** This is what the previous entry was missing, and it closes all
three of the opcodes it recorded as outstanding, not two of them. With three
early returns GCC cross-jumps them into a single block and places that block at
the *last* one, in the middle of the function; the target's is at the end, as
`.L80045314`. Once it is at the end, the delay-slot filler can steal its
`addu $v0, $zero, $zero` for the range check's branch and redirect that branch
to `.L80045318` - which is exactly the `bnez` polarity the previous entry
recorded as unreachable, and the separate exit block it recorded as
cross-jumped away. Both were the same cause. The twin does not have this
problem because it returns nothing, which is why it was already at 2 while this
one sat at 3.

Applied as a one-line change to the previous candidate - the three `return 0`
bodies replaced by `goto done` with `done: return 0;` at the end - it goes
straight from 74 instructions and opcode distance 3 to 75 and 0.

**The parameter is `u16` and there are two parameters.** The matched
`src/game/sound_output_state.c` declares `extern s32 func_80045208(u16, s32);`
and `func_800451E0` calls it as `func_80045208(value, 0x80)`. The second
parameter really is unused: `$a1` is overwritten by the `g_SDValue` load in the
first two instructions. The previous entry took a single `s32`.

**The working copy is `u16`, which removes a pin.** Declared `u16 code`, the
`> 0x9FFF` comparison still produces `andi $v1, $s3, 0xFFFF` because the
comparison needs the truncated value, but `code = arg0 + 0x8000` no longer
needs one - the truncation is deferred to the `sh` into the request. Declared
`s32` it costs an `andi ..., 0xFFFF` in each of the two non-default arms. As a
`u16` the value also lands in `$s3` without `register s32 code asm("$19")`.

**The `$a1` pin on the `g_SDValue` pointer is not needed.** With the exit block
at the end, dropping it still gives 2. It is redundant on the twin as well -
`func_80045334`'s stored source reaches 70/70 and 2 differing with that pin
removed - so the previous "three register pins are needed" should read two:
the table pointer in `$v0` and the loaded word in `$s0`. The table pin is the
load-bearing one: unpinned, GCC coalesces the bank pointer with the word loaded
out of it, which forces `second` to be computed before the load and leaves the
`func_800464F0` delay slot empty, one instruction longer than the target.

Retained from the previous entry, because both still hold: the three-way test
is a `switch` and not an `if`/`else if` chain, or the handlers go inline and the
default stops being the fall-through; and the default arm reads
`code = code + 0x6000` rather than `code = arg0 + 0x6000`.

## What is left

Two positions - the order of the three word stores into the request block, and
therefore which one the delay-slot filler steals for `jal func_80045BE8`:

```
target   sw $s0, 0x14($sp)   sw $s1, 0x1C($sp)   jal ... / sw $s2, 0x18($sp)
build    sw $s2, 0x18($sp)   sw $s1, 0x1C($sp)   jal ... / sw $s0, 0x14($sp)
```

The previous entry established that source statement order is not the input
this order is computed from, over about 1800 variants, and that `volatile` is
the one control that reaches it but cannot finish because a `volatile` store
may not sink into the delay slot.

**What the order *is* computed from is how each stored value is produced.** A
ten-line probe isolates it; it is written up as its own section in
`notes/research/matching-evidence.md`. The store of a value produced by a load
is emitted last in the block, for every permutation of the source statements.
Change `first` so it comes from an `addiu` instead of a `lw` and the order
becomes the target's - and `first`/`second` swap their hard registers on their
own, with no pin. So the residue here is that the target's *first* store is
nevertheless the one fed by `lw $s0, 0x0($v0)`.

**The order is reachable after all, and the residue is now one pass, not two.**
The twin's entry identifies the pass as `sched2` and narrows the question to its
tie-break among three equal-priority stores; the same measurement below was made
on both entries and holds identically on each.
Marking all three word stores `*(volatile s32 *)&req.fNN = ...` in the target's
order reproduces that order exactly - `sw $s0, 0x14`, `sw $s1, 0x1C`,
`sw $s2, 0x18`, in the block, with no register or provenance change anywhere
else in the function. What it costs is the delay slot: `dbr` will not move a
volatile store into the `jal func_80045BE8` slot, so `addiu $a0, $sp, 0x10`
takes it and the whole five-store block shifts one position earlier. Six words
differ, but they are six words of *offset*, not of order.

So the two coupled unknowns separate. The scheduler's store order is
controllable; the remaining question is only how retail got a store that the
delay-slot filler was willing to take while keeping that order.

Three further facts from the same sweep, all measured on this base at
`gcc_2_8_1_g0`:

- **`volatile` is not a barrier for non-volatile stores in this scheduler.**
  With `f04` and `f0C` volatile and `f08` left plain, the plain store hops
  *above* both volatile ones and lands first. Only volatile-versus-volatile is
  ordered, which is why the all-three form is the one that works.
- **A volatile store is free to sit in the middle of the block.** With only
  `f08` volatile the emitted order is `f0C`, `f08`, `f04` - so the refusal is
  specific to the delay slot, not to motion in general.
- **The provenance rule is two-sided, not one-sided.** The previous note reads
  as "a load-produced store goes last"; the constant-produced store going
  *early* is the same rule seen from the other end, and it is what puts
  `sw $s2` first in every unconstrained build. Retail has the constant-produced
  store last and the load-produced store first, which is the inversion of both
  halves at once.

Measured placements, differing words: `f08` alone 3, `f0C` alone 3, `f04` alone
6, `f04`+`f0C` 4, `f04`+`f08` 5, `f0C`+`f08` 3, all three 6. The base without
any is 2, so no placement beats it on count - the all-three form is worth
recording because of *which* difference it leaves, not because of the count.

Also crossed on this base without improving on 2: all six permutations of the
three stores in both the struct form and the `u8 req[0x30]` form that the same
file's `func_80045114` uses, with both definition orders (24 combinations, all
byte-identical output); all 63 non-empty subsets of register pins over the
state pointer, table, `first`, `second`, `kind` and `code`; every GCC 2.8.1
profile; `second` as `u8 *` at `+8` and as `&table[2]`; non-void return types
on `func_800464F0`, `func_80045BE8` and `func_80044DA0`; and moving the two
stores above the call, which GCC will not sink back across it because `req`'s
address is taken. `gcc_2_8_1_g0_no_sched2` does emit the stores in source
order, but the rest of the function needs sched2 - the same source is 73
differing there.

### The residual is shared with the neighbouring candidate, and is not scheduling

`func_80045334` and `func_80045208` have the **same two differing positions**,
in the same shape: three stores into a stack `Request` struct immediately
before `jal func_80045BE8`, where one of them lands in the branch delay slot.

```
build    sw s2,24(sp) / sw s1,28(sp) / jal / sw s0,20(sp)
target   sw s0,20(sp) / sw s1,28(sp) / jal / sw s2,24(sp)
```

The build emits the three in descending hard-register order and the target in
ascending order, so the store that falls into the delay slot is the wrong one.

**Neither scheduling pass produces this.** `-fno-schedule-insns` leaves the
order unchanged at 2. `-fno-schedule-insns2` also leaves this pair in the build
order, while costing 67 positions elsewhere, so `sched2` is both required and
not responsible. The order is fixed during RTL generation, which puts it in the
same class as the `func_8005B36C` match: emission order follows value creation,
not source statement order.

**Exhaustively ruled out.** All six permutations of the three field assignments
were compiled: the source order and two others give 2, the remaining three give
3. None reaches zero. Reordering the local declarations to match the register
order, and pinning `first`, `second` and `kind` to `$16`, `$17` and `$18`
explicitly, are both neutral at 2.

**One pin is not load-bearing and should be dropped if this is revisited:**
removing the `$5` pin on `a` keeps the count at 2. The others are: unpinning
`first` costs 3, `code` 14, and `table` 32.
