The globe wireframe. It draws a latitude/longitude sphere with the
`func_80029684`/`func_800297DC` projection-axis pair immediately below it in the
image, which are matched and share this translation unit's idiom.

### Scratchpad layout

Everything it works on lives in PSX scratchpad at `0x1F800000`, and naming it
is most of what makes the body readable:

| address | what |
| --- | --- |
| `0x1F800000` | a **`LINE_G3`** primitive: byte 3 is the tag length 7, byte 7 the code `0x58`, `+0x08`/`+0x10`/`+0x18` the three `xy`, `+0x0C`/`+0x14` the two extra `rgb`, and `+0x1C` the `0x55555555` terminator |
| `0x1F800038`, `+0x40`, `+0x48`, `+0x50` | four `SVECTOR`, the `dst` argument of `func_80029684` (which indexes it as `dst[0]`, `dst[4]`, `dst[8]`) |
| `0x1F800060` | the `control` pair `func_80029684` passes to `RotAverage3`, with two more words after it holding the current ring radius and its offset |
| `0x1F800200` | eight bytes copied unaligned out of `D_80181000`, read back as the two centre coordinates |

The `0x58` code and the seven-word length are what identify the primitive; the
`0x55555555` in the eighth word is the standard line terminator, which is why
the tag length is 7 and not 8.

### What it does

`SetGeomOffset(0xD0, 0x60)` and `SetGeomScreen(0x12C)` set a 320x240-ish
projection, then `GsSetLsMatrix(&D_800FE148)`.

The first loop steps `angle` from 0 to `0x400` in eight `0x80` steps and draws
the **meridians**. Its colour ramp is `(0x400 - angle) * 0xFF / 0x400` written
into all three of the primitive's `rgb` slots, so the rings fade with latitude.
`rcos`/`rsin` scaled by `D_800EA1E8[8]` give the ring radius and its vertical
offset; the loop stops early the moment the radius rounds to zero, which is the
`beqz` that jumps straight to the second phase. Each ring is drawn as four
`func_80029684` calls and four `func_800297DC` calls, the second pair of each
guarded on `angle != 0` so the equator is not drawn twice.

The second loop steps `angle` from 0 to `0x1000` and draws the **parallels**.
Each iteration builds two points from `rcos`/`rsin` at `angle` and
`angle + 0x80`, projects both through the GTE, and then walks the pair down the
screen in seven steps of `radius / 10`, emitting a `func_8005B260` line each
time and stopping as soon as the y coordinate goes non-positive.

Three calls close it out: `func_800540B4(0)`, `func_800559D4(0)`,
`func_800556E8(0)`.

### Levers

- *Signed division, not a shift.* Every `>> 12` has to be written `/ 4096`, and
  the `0x66666667` sequence is `/ 10`. Retail's `bgez`/`addiu 0xFFF`/`sra`
  triples are the rounding correction GCC emits for signed division by a power
  of two; writing shifts loses six `bgez` and twelve instructions in total.
  This was worth 334 -> 344 on its own.
- *The unaligned eight-byte copy.* `D_80181000` is a `u8[]`, so a struct
  assignment through an eight-byte char struct is what produces retail's
  `lwl`/`lwr`/`swl`/`swr` quartet. Two `s32` loads do not.
- *Three stores use absolute addresses, not the primitive base.* Retail writes
  `0x1F800042`, `0x1F80004A` and `0x1F800052` with a `lui $at` each rather than
  as an offset from a register it already holds, which only happens when the
  source spells them as integer constants.
- *`rcos` is not in the step expression.* The second loop's scale factor is
  `D_800EA1E8[8] + 0x80`, read by the `lh` sitting in the `jal rcos` delay
  slot. Reading it as `rcos(angle) + 0x80` gives a fifth trigonometric call and
  the wrong operand order throughout the loop.
- *One temporary for the repeated `+0x0A` read.* Retail loads the primitive's
  y once and stores the same value to `+0x12` and `+0x1A`.
- *A block-scoped pointer for `D_800EA1E8` in the first loop.* Retail
  rematerialises `lui`/`addiu` after each of the two trigonometric calls
  because the address lives in the caller-saved `$t2`; the array subscript
  folds `%lo` into the `lh` and is two instructions short. This is worth 36
  differing words.

### GTE

The two projections are `lwc2 $0`/`lwc2 $1`, `rtps`, `swc2 $14`. This tree's
`src/psyq/inline_c.h` defines `gte_rtps()` as `.word 0x0000007f`, which is the
SN marker word and assembles to the wrong four bytes under binutils, so the
entry uses the tree's own established alternative: a `__asm__ volatile` block
with `".word 0x4A180001" /* rtps */`, exactly as the matched
`display_projection.c`, `func_8001B0CC.c`, `func_800177C4.c` and
`func_800178BC.c` already do. **Both `rtps` words are byte-identical to
retail**; the opcode histogram reports them as `c2` only because objdump names
a bare `.word` differently from splat.

### What is left

Two things, both allocation.

- **One address materialisation.** The second `D_800EA1E8` pointer in the first
  loop is common-subexpression-eliminated with the first, so retail's second
  `lui`/`addiu` pair is missing. Both uses are in one region and block scope
  does not separate them here, unlike the four-arm case in `func_8004ADE8`
  where it did.
- **`D_800E9D9C` spills.** Retail keeps it in `$s6` across both loops; this
  build stores it and reloads it twice, which is the `lw +2`/`sw +1`. The two
  are linked: the pointer variable that fixes the first takes the
  callee-saved register the second needs. Nine saved registers are live in
  retail (`angle`, the four `SVECTOR` pointers, the control and parameter
  pointers, the primitive pointer and this one) and there is no tenth.
  Using the array subscript instead trades one problem for the other at 351
  instructions either way -- 267 differing rather than 231.

The prologue also interleaves the scratchpad constant materialisations with the
register saves in a different order; that is scheduling, not content.
